# 2. 출입 인증 및 실시간 관제 — 초보자를 위한 구현 해설

분석일: 2026-10-26. 로컬 소스 정적 분석이며 이번에 실제 카메라·DB·네트워크를 실행하지 않았다. 예시 이름과 상황은 설명용이다.

## 1. 이 기능이 해결하는 일

얼굴 AI가 직원 A를 후보로 찾았다고 하자. 직원 A가 퇴사했거나 현재 출입 권한이 없다면 출입을 허용하면 안 된다. 이 기능은 클라이언트의 식별 결과를 서버가 검증하고, 현재 DB의 직원·등록·장치·권한 상태를 확인해 최종 결과를 기록하고 돌려주는 과정이다.

관리 서버는 화면을 보여주는 WPF 앱이면서 통신과 DB 처리를 수행하는 서버다. 화면과 서버가 별도의 배포 앱인 구조로 설명하면 안 된다. 실제 문 개폐 장치 제어는 이 문서에서 확인한 범위가 아니다.

## 2. 세 가지 흐름을 구분한다

| 흐름 | 전달하는 것 | 목적 |
|---|---|---|
| 얼굴 분석 결과 | 직원 후보, 거리, 등록 ID, 분석 나이, 시도 ID | 서버 판정 |
| 실시간 영상 | JPEG 프레임 | 관리자가 현재 상황 확인 |
| 녹화·클립 파일 | MP4와 관련 메타데이터 | 과거 조회·보관 |

실시간 영상이 보인다고 최신 얼굴 분석 결과가 도착한 것은 아니다. 얼굴 분석이 늦어도 영상은 계속 갱신될 수 있어, 코드가 두 상태를 따로 관리한다. 영상 전체를 서버에서 다시 분석하는 구조도 아니다.

## 3. 전체 요청·응답 과정

1. Python AI가 현재 얼굴의 분석·식별 결과를 만든다.
2. 인증 앱이 결과가 최신이며 현재 적용된 직원 기준과 맞는지 확인한다.
3. `ObservationSource`가 서버 전송용 관측 상태로 변환한다.
4. `MonitorClient`가 상태를 서버로 보낸다.
5. `MonitorServer`가 메시지를 받아 서버 DB 판정 함수를 호출한다.
6. 서버가 유효성·권한을 검사하고 DB에 이벤트를 저장한다.
7. 저장을 완료한 서버가 결과와 이벤트 ID를 응답한다.
8. 인증 앱과 서버 화면에 허가·거부 또는 대기·오류를 표시한다.

여기서 응답은 요청을 받았다는 뜻만이 아니다. 최종 응답의 `Recorded`와 `EventId`는 DB 기록 완료 여부를 나타내는 중요한 정보다.

## 4. Python 결과를 그대로 믿지 않고 변환하는 이유

`FaceRecognition/ObservationSource.cs`의 `Update()`가 여러 조건을 확인한다.

- 분석 결과가 최신인지 확인한다.
- AI의 상태가 정상인지 확인한다.
- 보정이 끝났고 비교 중이며 등록 중이 아닌지 확인한다.
- 유효한 등록 샘플 수와 숫자 범위를 확인한다.
- 1위·2위 후보가 모호하지 않은지 확인한다.
- 비교 거리와 일치 여부가 서로 일관적인지 확인한다.

통과한 경우에만 `MATCH_CANDIDATE` 또는 `NO_MATCH` 상태로 만든다. 그 외에는 기다림이나 보류 상태를 보낸다. 얼굴이 보이지 않거나 결과가 오래된 상태를 ‘권한 없음’으로 뭉뚱그리지 않는 것이다.

### 서버에 전달하는 주요 값

| 값 | 쉬운 설명 |
|---|---|
| PersonId | 후보 직원의 고유 번호 |
| EnrollmentId | 어떤 얼굴 등록으로 비교했는지 |
| Lease | 서버가 해당 등록에 대해 발급한 참조 토큰 |
| Distance | 얼굴 특징 간 거리 |
| RunnerUpDistance | 두 번째 직원 후보의 거리 |
| AnalysisAgeMs | 결과가 만들어진 프레임·분석이 얼마나 오래됐는지 나타내는 값 |
| AttemptId | 현재 인증 시도를 구별하는 번호 |
| SentAt | 메시지 전송 시각 |

Lease는 출입 허가증이 아니다. 서버가 알고 있는 직원·등록 조합인지 검증하기 위한 참조 토큰이다.

## 5. 오래된 결과를 막는 방법

`Network/MonitorProtocol.cs`의 `MaxAnalysisAgeMs`는 2500ms다. `ObservationSource.Get()`은 보관 중 경과 시간도 결과 나이에 더한다. 서버 `AccessPolicy.IsCurrent()`는 전송에 걸린 시간까지 고려한다.

예를 들어 분석 나이 2000ms인 결과가 전달에 700ms 걸렸다면 합계는 2700ms다. 코드의 한도를 넘으므로 최신 판정 근거로 사용하지 않는다. 이것은 설명용 예시이며 실제 지연 측정값이 아니다.

서버의 DB 처리에도 남은 유효 시간에 따른 취소 제한을 적용하고 저장 직전 최신성을 다시 확인한다. 허용 범위가 남지 않으면 새 분석을 기다린다. 따라서 2500ms는 처리 속도 보장이나 응답시간 목표를 측정한 값이 아니다.

## 6. 서버는 무엇을 확인하는가

핵심은 `AccessControlServer/AccessEventDatabase.cs`의 `DecideAsync()`다.

### 6.1 기본 검증

판정 가능한 상태인지, 인증 시도 ID가 있는지, 후보가 모호하지 않은지, 최신인지 확인한다. 참조 토큰이 실제 발급된 직원·등록 조합과 같은지도 확인한다. 비교할 기준이 없으면 정상 거부 이벤트와 구분해 오류·대기로 처리할 수 있다.

### 6.2 현재 DB 상태 조회

| 조회 대상 | 확인할 내용 |
|---|---|
| cameras + client_instances | 등록된 인증 장치인지, 장치가 활성 상태인지 |
| persons | 직원이 활성 상태인지, 출입 권한이 켜져 있는지 |
| face_enrollments | 해당 등록이 유효하며 모델·512차원 조건이 맞는지 |

DB에서 최신 상태를 읽으므로 클라이언트가 예전에 받은 권한을 최종 허가 기준으로 삼지 않는다. 직원·등록 기준 동기화와 최종 권한 확인은 역할이 다르다.

### 6.3 정책 결정

`Network/AccessDecision.cs`의 `AccessPolicy.Evaluate()`는 다음 순서로 판단한다.

1. 장치가 비활성이면 거부한다.
2. 얼굴이 일치하지 않으면 거부한다.
3. 직원이 비활성이면 거부한다.
4. 얼굴 등록이 비활성이면 거부한다.
5. 출입 권한이 있으면 허가하고, 없으면 거부한다.

이보다 앞선 최신성·토큰 검증에서 실패하면 이 정책까지 진행하지 않을 수 있다. 모든 실패를 DENIED로 기록하는 구조는 아니다.

## 7. 판정과 기록을 한 과정으로 묶는다

서버는 DB 트랜잭션 안에서 정보를 조회하고 `access_events`에 결과를 추가한다. SQL은 문자열에 사용자 값을 직접 이어 붙이지 않고 `@person`, `@camera` 같은 매개변수를 사용한다.

이벤트에는 카메라, 직원·등록 ID, 이벤트 시각, 결과, 사유, 비교 값이 담긴다. 불일치 시 직원·등록 연결은 비워 미등록자를 특정 직원으로 기록하지 않는다. DB 스키마에는 유사도를 저장하므로 코드의 거리 `d`를 `1 - d`로 변환한다. 거리와 유사도의 방향을 PPT에서 뒤집지 않도록 주의한다.

저장 후 기록을 다시 조회해 내용이 일관적인지 확인하고 트랜잭션을 완료한다. 그다음 `Recorded=true`인 판정을 돌려준다. DB 오류 시 `ERROR / DB_ERROR`로 처리해 출입 허가를 보류한다.

## 8. 같은 사람이 서 있을 때 기록이 계속 쌓이지 않게 하는 방법

카메라는 계속 프레임을 보내므로 매번 새 출입이라고 기록하면 한 번의 인증이 수십 건으로 남을 수 있다.

`AuthenticationAttempt.Observe()`는 비교 대상·상태가 유지되는 동안 시도 ID를 유지한다. 비교가 바뀌거나, 비교 중단 뒤 약 2초 이상 지나 다시 시작하면 새 시도로 구분한다. 정확한 횟수는 영상·상태 변화에 따라 달라진다.

서버는 시도 ID, 카메라, 결과·사유, 직원·등록 및 정책 버전으로 안정적인 이벤트 ID를 계산한다. DB의 `ON CONFLICT(event_id) DO NOTHING`으로 같은 ID의 재전송을 중복 추가하지 않는다. 정책이 바뀌면 같은 시도라도 다른 이벤트가 될 수 있으므로 ‘한 사람이면 언제나 딱 한 건’이라는 보장은 아니다.

## 9. 실시간 영상은 어떻게 관제 화면에 나타나는가

인증 앱 `MainWindow.xaml.cs`는 `panel.LiveFrameUpdated` 이벤트에서 프레임을 받아 영상 전송원에 제공한다. 서버는 수신 JPEG를 화면에 표시하고 관측 상태와 판정도 별도로 갱신한다.

기본 상태 포트는 5050이며, 영상 채널은 기본 포트의 다음 포트, 얼굴·미디어 API는 그다음 포트를 사용하는 구조다. 실제 보안·연결 모드는 설정과 `LinkSecurity` 구현을 함께 확인해야 한다. 최신 버전의 선택형 암호화 설정을 무시하고 모든 경로가 항상 TLS라고 설명하면 안 된다.

서버 화면은 마지막 수신 시각을 확인하고 응답이 없으면 이전 비교 결과를 숨긴다. 연결된 것처럼 예전 허가 표시를 계속 보여주는 상황을 줄이기 위한 처리다.

현재 코드는 `CAM-01` 등 단일 카메라 기준 경로가 있으며, 다중 카메라 확장 가능성과 실제 다중 카메라 동시 지원·검증은 구분해야 한다.

## 10. 상황별 설명 예시

| 상황 | 예상되는 처리 방향 |
|---|---|
| 얼굴 일치, 직원·장치·등록 정상, 권한 있음 | DB 기록 후 GRANTED |
| 얼굴 일치, 권한 없음 | DB 기록 후 DENIED / ACCESS_DISABLED |
| 1·2위 직원의 점수가 너무 비슷함 | 모호성 사유로 보류 |
| 오래된 얼굴 결과 | 새 분석 대기 |
| 서버 DB 처리 실패 | 오류 표시, 허가 보류 |
| 영상만 정상이고 분석은 멈춤 | 관제 영상과 인증 상태를 구분해 표시 |

이는 조건을 설명한 표이며 이번 실행 결과표가 아니다.

## 11. 소스 읽기와 PPT 활용

| 소스 경로 | 확인할 역할 |
|---|---|
| FaceRecognition/MainWindow.xaml.cs | 갤러리·AI 상태 연결, 영상 전달, 판정 표시 |
| FaceRecognition/ObservationSource.cs — Update/Get | 최신·유효 결과의 관측 메시지 변환 |
| Network/MonitorProtocol.cs | 메시지 필드와 시간 제한 |
| Network/MonitorClient.cs, MonitorServer.cs | 상태 요청·응답 |
| Network/AccessDecision.cs | 정책·시도 ID·이벤트 ID |
| AccessControlServer/AccessEventDatabase.cs — DecideAsync | DB 검증·판정·기록 |
| AccessControlServer/MainWindow.xaml.cs | 서버 판정 콜백과 관제 표시 |

경로 기준은 `AccessControl_UI`다. PPT에는 권한 있는 직원과 권한 없는 직원 사례를 나란히 보여주고, ‘클라이언트는 후보를 찾고 서버는 현재 권한을 확인한다’는 책임 분리를 설명한다. 전체 SQL 대신 실제 판정 조건과 기록 결과를 대응시키면 초보자도 이해하기 쉽다.

발표 문장: ‘얼굴 식별 결과를 받은 서버가 현재 직원·장치·권한을 확인하고, DB 기록이 끝난 뒤 최종 허가·거부를 돌려주도록 구현했습니다.’

문제 해결 근거는 [트러블슈팅](../troubleshooting.md)의 TS-04·07·14다. 과거 통과 기록과 최신 Windows 현장 확인을 구분하고, 다중 카메라·실제 문 제어·정확도 측정을 구현 성과로 확대하지 않는다.
