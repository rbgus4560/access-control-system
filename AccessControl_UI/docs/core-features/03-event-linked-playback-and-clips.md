# 3. 출입 기록 기반 영상 조회 — 초보자를 위한 구현 해설

분석일: 2026-10-26. 로컬 소스 정적 분석이며 이번 작업에서 실제 녹화·DB·재생·파일 전송을 실행하지 않았다. 시간 예시는 이해를 위한 가상 값이다.

## 1. 이 기능의 목적

‘10시 15분에 출입 거부가 있었다’는 기록만으로는 당시 상황을 알기 어렵다. 사용자가 기록을 선택하면 같은 카메라의 해당 시점 영상을 찾아 재생하고, 필요한 시간 범위만 별도 클립으로 추출할 수 있도록 연결한 기능이다.

이 기능은 실시간 관제와 다르다. 관제는 지금 들어오는 JPEG를 보여주고, 과거 재생은 이미 저장된 MP4를 찾아 연다.

## 2. 무엇을 어디에 저장하는가

| 데이터 | 위치·담당 | 쉬운 비유 |
|---|---|---|
| 원본 녹화 MP4 | 인증 클라이언트의 로컬 저장소 | 책의 본문 |
| 구간 JSON | 클라이언트, MP4 옆의 구간 설명 | 책의 색인표 |
| recording_segments | 서버 PostgreSQL의 시간·카메라·상태 정보 | 검색 가능한 도서 목록 |
| access_events | 서버 PostgreSQL의 출입 판정 기록 | 사건 일지 |
| 서버 재생 캐시 | 요청해 받은 원본 영상 사본 | 읽으려고 가져온 책 |
| exported_clips | 서버 DB의 클립 작업·결과 정보 | 발췌본 관리 목록 |
| 클립 MP4 | 생성 중 클라이언트 임시 영역, 수신 후 서버 보관 영역 | 필요한 부분만 발췌한 파일 |

영상 파일 자체를 DB BLOB으로 저장하는 구조가 아니다. JSON도 DB를 대체하는 전체 환원본이 아니라 로컬 구간 설명과 재전송 근거로 사용한다.

## 3. 녹화 파일은 어떻게 만들어지는가

`FaceAI/segment_recorder.py`의 `SegmentRecorder`가 담당한다.

1. 카메라에서 들어온 프레임을 녹화기에 제공한다.
2. 새 구간 ID를 만들고 MP4와 JSON 경로를 정한다.
3. JSON에 `RECORDING` 상태와 시작 시각·화면 크기 등을 기록한다.
4. OpenCV의 `VideoWriter`로 프레임을 MP4에 쓴다.
5. 구간이 끝나면 파일을 닫고 다시 열어 읽기·프레임 수를 확인한다.
6. 프레임 수, 종료 시각, 크기와 최종 상태를 JSON에 반영한다.

기본 설정은 **10fps, 60초 단위, mp4v 인코딩**이다. 60초 × 10fps면 정상 완료 구간의 기준 프레임 수는 600개다. 실시간 화면의 30fps 목표와 녹화 10fps는 다른 설정이며, 둘을 같은 성능 결과로 설명하면 안 된다.

영상 종료 시각은 시작 시각과 실제 기록 프레임 수/설정 fps를 사용해 계산한다. 이 방식이 카메라의 모든 실제 순간을 프레임 손실 없이 기록한다는 보장은 아니다. 시간 정합성은 실제 녹화 환경에서 검증해야 한다.

JSON은 임시 파일을 쓴 뒤 교체하는 방식으로 갱신한다. 쓰다가 프로그램이 꺼져 설명 파일의 절반만 남는 위험을 줄이는 처리다. 시작 시 미완료 녹화도 점검하는 복구 코드가 있다.

## 4. 서버가 로컬 녹화의 존재를 어떻게 아는가

`FaceRecognition/RecordingSync.cs`가 로컬 구간 JSON을 읽어 서버에 메타데이터를 보낸다.

1. 폴더를 순회해 구간 설명을 읽는다.
2. 파일 크기·내용·경로·상태를 검증한다.
3. 서버의 DB 세션을 확인한다.
4. 아직 확인 응답을 못 받았거나 내용이 바뀐 구간을 전송한다.
5. 서버가 저장했다고 확인한 내용만 ACK 대상으로 기억한다.

ACK는 ‘받았고 처리했다’는 확인 응답이다. 이 확인 목록은 메모리 최적화이며, 재시작 뒤 재시도 근거는 디스크 JSON에 남는다. 서버 세션이 바뀌면 기존 확인 목록을 비워 재전송할 수 있게 한다.

중요한 점은 **구간 정보 동기화와 MP4 파일 전송이 다른 작업**이라는 것이다. DB에 구간이 있다는 사실만으로 서버에 MP4가 이미 있다는 뜻은 아니다.

## 5. 서버 연결이 끊기면 어떻게 되는가

서버와 분리된 클라이언트 로컬 녹화 구조이므로 클라이언트·카메라·녹화 프로세스가 정상이라면 서버 연결이 끊겨도 녹화를 이어갈 수 있다. 서버가 복구되면 로컬 JSON을 근거로 정보를 다시 보낸다.

그러나 클라이언트 종료, 카메라 장애, 저장 공간 부족까지 모두 해결한다는 뜻은 아니다. ‘서버 장애 중 로컬 녹화 유지’와 ‘모든 장애에서 무손실’은 구분한다.

전송 실패는 구간별로 격리하고 시도 순서를 순환시킨다. 예전 실패 한 건 때문에 나중의 정상 구간이 영원히 전송되지 않는 문제를 줄인다. 관련 과거 장애는 기존 트러블슈팅 TS-08·09에 기록되어 있다.

## 6. 출입 기록을 누르면 어떤 일이 일어나는가

### 6.1 선택한 기록을 DB에서 다시 확인한다

`AccessControlServer/EventPlaybackDatabase.cs`의 `PlaybackEventAsync()`는 이벤트 ID로 출입 기록을 조회한다. 카메라 코드와 이벤트 시각, 직원·결과 설명을 얻는다. 화면에서 임의 파일 경로를 받아 여는 방식이 아니다.

현재 이 함수에는 **CAM-01만 재생 지원**이라는 명시적 검사가 있다. PPT에서 다중 카메라 기록 재생이 모두 구현됐다고 표현하면 안 된다.

### 6.2 그 시각을 포함하는 녹화 구간을 찾는다

`PlaybackPanel.OpenEventAsync()`는 해당 날짜의 구간 정보를 읽고 `RecordingTimeline.FindAt()`으로 이벤트 시각을 포함하는 구간을 찾는다.

예를 들어 이벤트가 10:15:23이고 구간이 10:15:00~10:16:00이면, 그 MP4의 시작에서 23초 위치를 재생하면 된다. 코드의 기본 계산은 `이벤트 시각 - 구간 시작 시각`이다.

### 6.3 파일을 준비하고 해당 위치에서 재생한다

`PlaybackPanel.PlayAt()`이 파일 준비 콜백을 호출한 뒤 미디어를 연다. 미디어가 열린 후 `media.Position`을 계산한 오프셋으로 설정한다. 영상이 없거나 만료·전송 실패·재생 불가 상태면 실패를 알려야 하며, DB 기록만 존재한다고 재생 성공을 보장하지 않는다.

## 7. 서버에 없는 원본 영상은 어떻게 가져오는가

서버 `MediaCoordinator.PrepareAsync()`와 클라이언트 `MediaAgent`가 협력한다.

1. 서버가 캐시 파일과 구간 설명·크기·해시를 확인한다.
2. 유효한 캐시가 없으면 연결 상태와 보관 기간을 확인한다.
3. 서버가 `segment` 요청에 구간 ID 등을 담아 보낸다.
4. 클라이언트 에이전트가 해당 로컬 구간을 확인해 전송한다.
5. 서버가 파일을 검증하고 수신 완료를 확인한다.
6. 준비된 캐시 MP4를 재생기에 넘긴다.

파일의 저장 목적지는 서버가 정한다. 클라이언트가 보낸 임의 경로를 그대로 서버 쓰기 경로로 쓰는 방식이 아니다. SHA-256 해시는 파일 내용으로 계산하는 확인값이다. 전송 전후 해시를 비교하면 전송된 바이트가 같은지 확인할 수 있지만, 영상 속 사실이나 얼굴 인식의 정확성을 검증하는 수단은 아니다.

## 8. 필요한 시간만 클립으로 만드는 과정

사용자가 시작·종료 시각을 선택하면 다음 작업이 진행된다.

| 단계 | 담당 코드 | 하는 일 |
|---|---|---|
| 요청 | ServerClipWindow | 시간 범위와 출입 이벤트 연결 여부 입력 |
| 작업 등록 | MediaCoordinator.ExportAsync | 클립 ID 생성·DB 작업 시작 |
| 요청 보존 | MediaCoordinator.ExecuteClip | 재시작 후 복구할 작업 JSON 작성 |
| 현장 처리 | MediaAgent, ClipExporter | 클라이언트에서 원본 구간을 찾아 Python 실행 |
| 영상 추출 | FaceAI/export_clip.py | 필요한 프레임을 읽어 새 MP4 생성 |
| 전송·완료 | MediaCoordinator, ClipDatabase | 결과 검증·서버 저장·DB 상태 완료 |

출입 이벤트 ID는 클립이 어느 기록과 관련되는지 연결하는 값이다. 클립 전체를 반드시 한 이벤트에 연결해야 하는 것은 아니며 UI에 선택 처리가 있다.

### Python 추출 코드의 세부 처리

`export_clip.py`는 카메라나 얼굴 모델을 새로 열지 않는다. 저장된 파일만 처리하는 독립 작업이다.

1. 출력 경로가 허용된 클립 폴더인지 확인한다.
2. 입력 구간 수, 10fps, 크기와 요청 길이를 검증한다.
3. 각 원본의 시작 프레임과 읽을 프레임 수를 검증한다.
4. 시작 프레임까지 순서대로 건너뛴 뒤 필요한 프레임을 읽는다.
5. 여러 구간에 걸친 프레임을 하나의 MP4에 이어 쓴다.
6. 결과 MP4를 다시 열어 첫 프레임과 전체 프레임 수를 검증한다.
7. 크기·프레임 수·길이·SHA-256을 결과로 반환한다.

코드상 요청 길이는 0초 초과·최대 300초이며, 구간 수 등 추가 제한도 있다. 10fps 기준으로 프레임 경계에 맞춰 처리하므로 ‘어떤 영상도 무제한 길이로 밀리초 단위 정확 추출’이라고 설명하면 안 된다.

## 9. 상태를 나누는 이유

| 상태·상황 | 의미 |
|---|---|
| 녹화 RECORDING | 파일을 작성 중 |
| 녹화·클립 READY | 해당 단계에서 사용 가능한 결과로 판정 |
| 클립 FAILED | 요청 완료가 불가능한 실패로 확정한 상태 |
| 재시도 대기 | 통신·DB 등 복구 가능한 조건을 기다리는 상태 |

READY가 모든 PC에서의 최종 재생 실험 성공을 뜻하지는 않는다. 단계별 검증과 실제 UI 재생을 구분해야 한다.

서버는 `.remotejob.json` 작업을 남기고 DB 완료 반영에 성공한 뒤 지운다. 파일을 받았지만 DB 처리가 실패한 경우 완료 반영을 재시도할 수 있다. 완료 불가능한 요청을 끝없이 대기로 남기지 않도록 영구 실패와 일시 실패도 구분한다.

서버 클립과 클라이언트 임시 클립의 저장 폴더를 나눠, 같은 PC에서 시험할 때 임시 파일 정리가 서버 보관 파일에 간섭하지 않게 한다. 임시 클립은 서버 수신 확인과 관련 처리를 거친 뒤 정리한다.

## 10. 보관 기간과 한계

기본 원본 보관 정책은 완료 후 72시간이며 사용 중 파일은 정리를 미룬다. 72시간은 녹화 길이나 서버 장애 허용 시간을 보장하는 수치가 아니다. 만료 원본이 이미 사라졌다면 과거 출입 기록이 남아 있어도 그 영상을 새로 만들 수 없다.

따라서 실제 확인할 항목은 서버 중단 중 녹화, 재연결 후 구간 목록, 해당 시점 재생, 구간 경계 클립, 전송 중단, 만료 파일, 저장 공간·DB 실패다. 현재 문서 작성에서는 이를 실행하지 않았다.

## 11. 소스 읽기 순서와 발표 자료

경로는 `AccessControl_UI`를 기준으로 한다.

| 순서 | 파일 | 읽을 이유 |
|---|---|---|
| 1 | FaceAI/segment_recorder.py | MP4·구간 JSON 생성 |
| 2 | FaceRecognition/RecordingSync.cs | 메타데이터 재전송·확인 응답 |
| 3 | AccessControlServer/RecordingDatabase.cs | 서버의 구간 저장·조회 |
| 4 | AccessControlServer/EventPlaybackDatabase.cs | 이벤트 ID를 카메라·시각으로 변환 |
| 5 | AccessControlServer/PlaybackPanel.cs | 구간 탐색·파일 준비·재생 위치 |
| 6 | AccessControlServer/MediaCoordinator.cs | 요청 큐·캐시·복구 작업 |
| 7 | FaceRecognition/MediaAgent.cs, ClipExporter.cs | 현장 파일 전달·Python 클립 실행 |
| 8 | FaceAI/export_clip.py | 프레임 추출·결과 확인 |
| 9 | AccessControlServer/ClipDatabase.cs | 클립 작업 상태 저장 |

PPT는 출입 기록 목록에서 한 건을 선택하는 화면, 그 시점 재생 화면, 클립 결과를 순서대로 보여준다. 옆에는 ‘파일은 현장에 저장, 검색 정보는 DB에 저장, 요청 시 서버로 전송’이라는 구조를 짧게 설명한다.

발표 문장: ‘출입 이벤트의 카메라와 시각을 이용해 녹화 구간을 찾고, 현장 파일을 서버로 가져와 해당 위치를 재생하도록 구현했습니다. 필요한 범위는 클라이언트에서 별도 MP4로 추출해 서버가 검증하고 보관합니다.’

## 12. 문제 해결과 연결할 소재

[기존 트러블슈팅](../troubleshooting.md)의 TS-08~11·15가 관련된다.

- 실패 구간이 신규 전송을 막는 문제: 구간별 실패 격리·순환 재시도.
- 과거 로컬 경로와 원격 구간 키 충돌: 식별자·상태 조건을 확인한 제한적 전환.
- 완료 불가능한 클립의 무한 대기: 영구 실패 확정과 DB 반영 재시도.
- 한 PC의 임시·서버 파일 간섭 위험: 소유 주체별 경로 분리.
- 원본 삭제와 재생 충돌 위험: 사용 중 파일 보관 정리 보류.

모든 항목이 실제 사용자 장애였던 것은 아니다. 기존 기록에 예방·회귀 시나리오로 분류된 항목은 그대로 구분한다. 과거 검사 통과·사용자 확인과 이번 독립 재현을 섞지 않는다.
