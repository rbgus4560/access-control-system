# 1. 얼굴 등록 및 자동 식별 — 초보자를 위한 구현 해설

분석일: 2026-10-26

## 읽기 전에

이 문서는 현재 로컬 `AccessControl_UI`의 C#·Python 소스와 기존 프로젝트 기록을 대조한 정적 분석이다. 이번 작업에서 카메라, 모델 추론, DB, 두 PC 통신을 실행하지 않았다. 수치는 코드의 설정이며 측정된 정확도나 속도가 아니다. 예시 직원과 점수는 설명용 가상 값이다.

이 기능의 목적은 직원의 얼굴을 먼저 등록하고, 나중에 카메라에 나타난 얼굴을 등록 직원들과 비교해 후보를 찾는 것이다. 여기까지의 결과는 ‘누구와 비슷한가’이며, 출입 허가는 서버가 별도로 결정한다.

## 1. 먼저 알아야 할 용어

| 용어 | 쉬운 설명 | 우리 코드에서의 의미 |
|---|---|---|
| 프레임 | 영상에서 꺼낸 사진 한 장 | 얼굴 분석의 입력 |
| 얼굴 검출 | 사진에서 얼굴 위치 찾기 | dlib 기반 검출 |
| 랜드마크 | 눈·코 등 얼굴의 기준점 | MediaPipe의 얼굴 위치·자세 분석에 사용 |
| 정렬 | 기울어진 얼굴의 기준을 맞추는 처리 | dlib의 눈 위치를 활용한 정렬 |
| 임베딩 | 얼굴의 특징을 숫자로 표현한 배열 | ArcFace의 512차원 특징 |
| 정규화 | 비교하기 좋게 숫자 크기를 맞추는 처리 | 특징 벡터의 길이를 1로 맞춤 |
| 갤러리 | 비교 대상인 직원 얼굴 특징 모음 | 서버에서 받은 직원별 등록 샘플 |
| 1:N 식별 | 한 얼굴을 여러 직원과 비교 | 직원 선택 없이 전체 갤러리 검색 |

512차원은 얼굴을 512개 부위로 나눴다는 뜻이 아니다. 모델이 만드는 512개의 숫자로 된 표현이다. 특정 숫자를 ‘눈 크기’처럼 직접 해석하면 안 된다. 사전학습 모델을 호출하는 구현이며, 우리 프로젝트에서 ArcFace를 직접 학습한 것은 아니다.

## 2. 누가 무엇을 하는가

| 구성 | 맡은 일 |
|---|---|
| FaceEnrollment | 관리자가 직원을 선택하고 얼굴 등록·저장을 진행하는 WPF 앱 |
| FaceRecognition | 현장 카메라에서 전체 직원 자동 식별을 수행하는 WPF 앱 |
| Shared/AiClient.cs | C#에서 Python 프로세스를 실행하고 명령·결과를 전달하는 연결 계층 |
| FaceAI | 얼굴 품질 확인, 자세 분석, 특징 추출, 샘플 선택과 비교 |
| 관리 서버 | 등록 요청 검증, PostgreSQL 저장, 직원 얼굴 기준 제공 |

C#과 Python은 한 프로그램의 함수처럼 직접 호출되는 것이 아니다. `AiClient`가 별도 Python 프로세스를 시작하고 표준 입출력으로 JSON 명령·결과를 주고받는다. 표준 입출력은 프로세스가 텍스트를 받고 내보내는 통로다. 영상은 JPEG를 포함한 메시지, 분석은 구조화된 상태 메시지로 구분한다.

## 3. 등록의 전체 순서

1. 관리자가 등록 앱에서 직원을 선택한다.
2. Python AI가 카메라의 얼굴을 분석한다.
3. 정면 보정 후 화면의 방향 안내에 맞춰 샘플을 수집한다.
4. Python이 조건에 맞는 대표 특징을 선택한다.
5. C#이 완성된 특징을 내보내기 요청으로 받는다.
6. 등록 앱이 서버에 선택 직원 ID와 특징을 전송한다.
7. 서버가 검증 후 DB 트랜잭션으로 새 등록을 저장한다.
8. 인증 클라이언트가 새 직원 기준을 자동으로 동기화한다.

‘등록 완료’와 ‘DB 저장 완료’는 다른 단계다. 얼굴 샘플을 만들었더라도 서버 저장이 실패하면 저장 성공으로 안내하면 안 된다.

## 4. 사진 한 장에서 얼굴 특징을 만드는 과정

실제 진입점은 `FaceAI/face_engine.py`의 `FaceEngine.observe()`다.

### 4.1 얼굴과 자세를 확인한다

코드는 BGR 프레임을 RGB로 바꾼 뒤 MediaPipe를 실행한다. 얼굴 랜드마크가 없거나 여러 얼굴이 있으면 유효한 단일 얼굴로 처리하지 않는다. 이어 dlib로 얼굴을 검출·정렬하고 검출 얼굴도 하나인지 확인한다.

MediaPipe는 자세와 랜드마크를, dlib는 검출·정렬을 맡는다. 이 단계의 실제 호출 순서는 MediaPipe 검사 후 dlib 검사다. 역할을 설명하는 그림의 나열 순서와 실제 코드 호출 순서를 혼동하지 않는다.

### 4.2 입력 품질을 검사한다

- 얼굴 영역의 짧은 변이 100픽셀보다 작으면 가까이 오도록 요구한다.
- MediaPipe의 코 위치가 dlib 얼굴 영역 안에 있는지 확인한다.
- 자세 변환 행렬의 모양과 숫자 유효성을 검사한다.
- 흐림·세부 정보 지표가 35보다 낮으면 특징 추출을 진행하지 않는다.
- 눈 위치를 통한 정렬 정보를 확인한다.

이 숫자는 품질 판정 설정이다. ‘35점 이상이면 정확도 35% 이상’이라는 뜻이 아니다. 두 검출 결과의 위치를 대조하는 것도 서로 다른 사람의 정보를 잘못 조합하지 않기 위한 검사다.

### 4.3 ArcFace 특징을 추출한다

`FaceEngine.embedding()`은 이미 검출·정렬한 얼굴을 `DeepFace.represent()`에 전달한다. 모델은 ArcFace이며 `detector_backend="skip"`, `align=False`로 중복 검출·정렬을 피한다. 반환 특징은 `unit_embedding()`으로 정규화한다.

## 5. 고개를 움직이며 등록하는 이유와 실제 선택 방식

현재 안내형 등록은 **정면 1개와 좌·우·상·하 각 2개, 총 9개 대표 샘플**을 만든다. 9방향을 따로 촬영한다는 뜻이 아니다.

`FaceAI/guided_enrollment.py`의 `GuidedEnrollment`가 수집 순서를 관리한다.

1. 정면 특징을 확보한다.
2. 현재 화면에 안내한 방향의 후보만 받는다.
3. 같은 방향에서도 서로 다른 각도의 후보를 모은다.
4. 각도 차이와 선명도를 고려해 두 샘플을 선택한다.
5. 다음 방향으로 넘어가기 전에 정면 복귀를 요구한다. 마지막 방향 뒤에는 전체 완료 조건을 검사한다.
6. 필요한 키가 모두 있어야 진행 중 샘플을 완성본으로 전환한다.

코드에서는 후보 풀을 방향당 최대 8개로 제한한다. 두 후보의 주축 각도 차이가 7도 이상이고, 좌우는 18도·상하는 14도 이상의 도달 조건을 만족하는 조합을 고른다. 등록 도중 정면 특징과 거리가 0.60보다 큰 특징은 다른 얼굴 가능성으로 거부한다. 이는 등록 일관성 검사이며 라이브니스 검사가 아니다.

후보 수집 간격과 안내 문구도 관리한다. 새 각도는 짧은 간격으로 받고, 유사한 각도의 반복 입력은 제한한다. ‘얼굴 등록 샘플을 늘렸으므로 정확도가 향상됐다’고 결론 내리려면 별도 비교 실험이 필요하다.

## 6. 서버와 DB에 어떻게 저장하는가

`FaceEnrollment/MainWindow.xaml.cs`의 `SaveDatabase()`를 보면 다음 정보가 서버로 전달된다.

| 항목 | 의미 |
|---|---|
| Operation = save | 얼굴 등록 저장 요청 |
| PersonId | 저장 대상 직원 ID |
| ExpectedEnrollmentId | 화면에서 알고 있던 기존 등록 ID |
| Reference | 완성된 얼굴 특징 모음 |

`ExpectedEnrollmentId`는 그사이 다른 등록이 생겼는지 확인할 수 있도록 전달하는 값이다. 직원 ID는 이름과 달리 대상을 구분하는 고유 번호다.

서버 `AccessControlServer/FaceDatabase.cs`의 `SaveAsync()`는 직원과 입력을 확인하고 DB 트랜잭션을 시작한다. 기존 활성 등록을 비활성화하고, 새 등록과 특징을 저장한 후 새 등록을 활성화한다. 트랜잭션은 여러 변경을 하나의 묶음으로 성공·취소하는 DB 기능이다. 중간에 실패한 상태가 정상 새 등록으로 남지 않게 한다.

| 테이블 | 저장 역할 |
|---|---|
| persons | 직원 정보 |
| face_enrollments | 어느 직원의 어떤 등록인지, 모델·차원·활성 상태 |
| face_templates | 등록에 속한 방향·샘플과 암호화된 특징 |

얼굴 특징은 Windows DPAPI의 CurrentUser 보호를 사용한다. 실행한 Windows 사용자 계정에 종속되는 보호이므로, DB만 다른 PC로 복사하면 아무 설정 없이 그대로 복호화된다고 가정하면 안 된다.

## 7. 새 등록은 인증 클라이언트에 어떻게 반영되는가

`FaceRecognition/GallerySynchronizer.cs`가 직원 목록을 주기적으로 조회한다.

1. 서버에서 목록과 DB 세션 정보를 받는다.
2. 바뀌지 않은 등록 특징은 메모리에서 재사용한다.
3. 새 등록이나 변경된 등록만 받아 검증한다.
4. 목록을 다시 읽어 수신 도중 등록이 바뀌지 않았는지 확인한다.
5. 완성된 목록만 새 스냅샷으로 공개한다.

각 작업 후 10초를 대기한다. 네트워크·처리 시간이 있으므로 ‘등록하면 반드시 10초 안에 반영’이라는 보장은 아니다. 동기화 실패·변경 중에는 인증을 보류한다.

Python의 `FaceGallery.begin/add/commit`도 임시 수신과 실제 사용 중인 갤러리를 나눈다. 예를 들어 10명 중 3명만 받았는데 그 목록을 전체 직원인 것처럼 사용하지 않도록 완성본을 한 번에 교체하는 방식이다.

## 8. 자동 식별은 어떻게 하는가

`FaceAI/face_gallery.py`의 `compare()`는 다음처럼 작동한다.

1. 새 얼굴의 특징 벡터를 만든다.
2. 저장된 전체 샘플과 코사인 거리를 계산한다.
3. 직원별로 가장 가까운 샘플을 대표 점수로 고른다.
4. 직원들을 거리순으로 정렬한다.
5. 1위 거리와 2위와의 차이를 함께 확인한다.

정규화한 벡터의 비교식은 `거리 = 1 - 두 벡터의 내적`이다. 거리가 작을수록 더 가깝다. 같은 직원의 서로 다른 자세가 1·2위를 차지했다고 모호한 두 사람으로 판단하지 않도록 직원별로 묶는다.

| 설명용 예시 | 코드 기준 결과 |
|---|---|
| 직원 A 0.30, 직원 B 0.50 | 1위가 0.45 이하이고 격차가 충분해 MATCH |
| 직원 A 0.30, 직원 B 0.33 | 격차가 0.05 미만이라 AMBIGUOUS |
| 직원 A 0.55, 직원 B 0.70 | 1위도 0.45를 초과해 NO_MATCH |

0.45는 거리 임계값이며 45%나 정확도 55%를 뜻하지 않는다. 직원 수 상한 1000명은 코드의 입력 제한이며, 1000명 환경에서의 속도 보장 수치가 아니다.

## 9. 파일을 읽는 순서

아래 경로는 `AccessControl_UI`를 기준으로 한다.

| 순서 | 파일·함수 | 확인할 부분 |
|---|---|---|
| 1 | FaceEnrollment/MainWindow.xaml.cs — SaveDatabase | 완성 특징을 서버에 저장하는 화면 동작 |
| 2 | Shared/AiClient.cs — Start, SendAsync, SendAppliedAsync | Python 실행·명령·적용 확인 |
| 3 | FaceAI/face_engine.py — observe, embedding | 품질 검사와 특징 추출 |
| 4 | FaceAI/guided_enrollment.py — wants, offer | 안내 방향별 샘플 선택 |
| 5 | AccessControlServer/FaceDatabase.cs — SaveAsync | 트랜잭션·특징 보호·DB 저장 |
| 6 | FaceRecognition/GallerySynchronizer.cs — RefreshAsync | 직원 기준 동기화 |
| 7 | FaceAI/face_gallery.py — commit, compare | 완성 갤러리 교체·1:N 비교 |

## 10. PPT에 담을 때

핵심 문장: ‘C# 등록·인증 앱에 Python 얼굴 분석을 연동하고, 완성된 직원 특징을 서버 DB에 저장한 뒤 자동 동기화해 전체 직원과 비교했습니다.’

화면은 등록 안내와 식별 결과를, 코드 근거는 `embedding()`과 직원별 점수 계산 일부를 고른다. 한 장에 모델 로딩·DB·동기화 전체 코드를 넣지 않는다. 등록과 식별 설명이 길면 두 장으로 나눈다.

질문 대비: ‘모델을 학습했나요?’에는 사전학습 모델을 연동했다고 답한다. ‘얼굴이 같으면 출입하나요?’에는 후보 식별 뒤 서버 권한 확인이 필요하다고 답한다. ‘사진 공격을 막나요?’에는 확인된 라이브니스 구현·평가가 없다고 구분한다.

관련 문제 해결은 [기존 트러블슈팅](../troubleshooting.md)의 TS-01·02·12·14를 참고한다. 아래 방향 수집 보완은 `docs/fixes/GUIDED_DOWN_20261022_KO.md`에 후속 기록이 있다. 현장 개선 효과는 해당 조건에서 재확인해야 한다.
