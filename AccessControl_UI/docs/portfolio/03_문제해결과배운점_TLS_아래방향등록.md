# 출입관제 문제 해결과 배운 점

TLS 연결 실패와 아래 방향 등록 정체를 한 슬라이드에 담기 위한 원고와 상세 설명입니다. 두 문제 모두 처리 단계를 나누고 로그·조건·시간 흐름으로 원인을 좁힌 경험으로 묶습니다.

### 한 슬라이드 배치

상단 제목은 “처리 단계를 나눠 연결 실패와 등록 정체 원인을 해결”로 둡니다. 가운데는 TLS 문제와 등록 문제를 좌우 두 칸으로 배치하고 각 칸을 문제·원인·해결 세 줄로 구성합니다. 하단에는 두 사례에서 배운 점을 한 문장으로 묶습니다. 아래 상세 내용을 슬라이드에 모두 넣지 않습니다.

### 왼쪽 칸 TLS 연결 실패

• 문제  TCP 포트는 열렸지만 앱 연결은 재시도·EOF 발생

• 원인  Windows TLS에서 서버 인증서 개인 키 사용 실패 로그 확인

• 해결  인증서 로딩을 UserKeySet으로 변경하고 개인 키 검사 추가

### 오른쪽 칸 아래 방향 등록 정체

• 문제  얼굴은 검출되지만 아래 방향 샘플 수집이 정체

• 원인  분석 0.2초와 수집 대기 0.45초가 충돌해 중간 각도 누락

• 해결  정면 복귀와 특징 수집을 분리하고 새 각도 0.18초·유사 각도 0.45초로 구분

### 하단 배운 점 한 문장

겉으로 보이는 성공과 실제 처리 완료를 구분하고, 단계별 로그와 상태·시간 조건을 확인해 원인을 좁히는 방법을 배웠습니다.

### 발표 시 검증 표현

TLS는 로그에 근거한 Windows 키 로딩 수정, 아래 방향 정체는 합성 시나리오로 재현한 수집 로직 수정입니다. 독립적인 실장치 재검증과 인식률 향상은 별도이며, 확인하지 않은 결과를 “모든 환경에서 완전 해결”이라고 발표하지 않습니다.

## 문제 1 TLS 연결 실패의 원인과 해결

### 무슨 일이 있었는가

서버의 TCP 5050 포트 접속 검사는 성공했지만 앱은 연결을 반복 재시도했습니다. 직원 조회에서는 unexpected EOF가 발생했고 Windows Schannel 이벤트 36869에는 TLS 인증서 개인 키 관련 오류가 기록됐습니다. 네트워크 포트 도달 이후의 TLS 인증 단계가 실패한 상황으로 나누어 보았습니다.

### 왜 포트 검사는 성공했는가

TCP 접속은 상대 주소와 포트까지 연결 가능한지 확인합니다. 그 다음 TLS는 인증서와 개인 키를 사용해 암호화 연결을 협상합니다. 따라서 TCP가 성공해도 TLS 단계에서 종료될 수 있습니다. EOF는 상대 스트림이 끝났다는 증상이지 그 자체가 방화벽·AI·DB 문제라는 뜻은 아닙니다.

### 확인한 원인과 코드

기존 Windows PFX 로딩은 EphemeralKeySet을 사용했습니다. 제공된 Schannel 로그와 Microsoft의 SslStream 문제 해결 안내를 근거로, Windows 보안 제공자가 개인 키를 사용할 수 있는 로딩 방식으로 바꿨습니다. 현재 코드는 Windows이면 UserKeySet, 다른 운영체제이면 EphemeralKeySet을 선택합니다. HasPrivateKey가 false이면 명시적으로 실패시킵니다.

### 무엇을 유지했는가

• 기존 인증서와 연결 토큰을 보존해 서버 신원을 임의로 바꾸지 않았습니다.

• TLS나 인증서 검사를 꺼서 우회하지 않았습니다.

• 직원 DB나 등록 얼굴 데이터를 수정해 해결한 문제가 아닙니다.

• PersistKeySet을 추가한 수정은 아닙니다. 사용자 키 영역 선택과 키 영구 보존은 같은 개념이 아닙니다.

### 검증과 발표 설명

“포트가 열려 연결 자체는 된다고 생각했지만, TLS 인증에서 별도로 실패하고 있었습니다. Schannel의 개인 키 오류를 확인해 Windows에서 인증서를 읽는 방식을 바꾸고 개인 키 검사를 추가했습니다. 이를 통해 접속·암호화 인증·앱 인증을 구분해서 확인해야 한다는 점을 배웠습니다.”

## 문제 2 아래 방향 등록 정체의 원인

### 비슷한 문제와 구분

이번 사례는 “고개를 숙이면 얼굴 검출이 끊기는 문제”와 다릅니다. 얼굴은 보이지만 아래 방향에서 필요한 서로 다른 두 시점을 모으지 못해 등록이 진행되지 않는 사례입니다. 검출·자세·수집 완료는 별도 조건입니다.

### 시간 순서로 이해하기

• 브리지는 약 0.2초마다 분석 결과를 만듭니다. 이전 수집 로직은 특징 샘플마다 0.45초 대기를 적용했습니다.

• 정면으로 돌아온 확인 단계까지 수집 시각을 갱신하면, 곧이어 아래로 움직이는 얕은 각도의 프레임이 대기 시간에 걸릴 수 있습니다.

• 다음으로 수집 가능한 때에는 이미 깊은 각도에 도달해, 대표 시점이 한쪽으로 몰릴 수 있습니다.

• 같은 깊은 각도를 계속 유지해도 두 샘플 사이 주축 각도 차이 7도 조건을 만족하지 못하므로 완료되지 않습니다. 단순히 오래 기다리라고 안내하는 것만으로 해결되지 않습니다.

### 합성 재현의 의미

정면 복귀 → 아래 10도 → 20도 입력을 5Hz로 제공한 시나리오가 수정 전에는 완료되지 않는 경로를 재현했습니다. 이는 수집 상태 머신과 대기 조건의 충돌을 보여줍니다. 실제 사용자 현상의 모든 원인을 이 경로 하나로 단정하지 않습니다. 실제 얼굴 자세·선명도·검출 조건도 영향을 줄 수 있습니다.

### 해결에 사용한 개념

• 상태 머신  정면 수집, 특정 방향 수집, 정면 복귀를 서로 다른 상태로 처리합니다.

• 샘플링 간격  새 시점 확보와 유사 시점 품질 갱신의 대기 시간을 구분합니다.

• 원자적 적용  필요한 대표 특징이 모두 완성된 뒤 활성 기준으로 교체합니다. 일부 수집이나 취소는 기존 기준을 보존합니다.

• 회귀 검사  문제를 일으키던 입력 순서를 자동 검사에 남겨 같은 코드 경로가 다시 막히는지 확인합니다.

## 문제 2 수정 내용과 공통 배운 점

### 구체적으로 바꾼 부분

• 정면 복귀는 특징 추출이 아닌 단계 전환으로 처리하고, 다음 방향의 첫 수집을 늦추지 않도록 마지막 추출 시각을 갱신하지 않습니다.

• 새 방향의 첫 샘플이나 기존 후보와 주축 7도 이상 다른 시점은 최소 0.18초 후 허용합니다. 약 0.2초 분석 주기에서 다음 새 시점을 받기 위한 여유입니다. 실측 최적값은 아닙니다.

• 유사 각도의 품질 교체에는 기존 0.45초 간격을 유지합니다. 모든 제한을 무조건 줄인 것이 아닙니다.

• 선명도 35, 정면 특징과의 거리 0.60, 각도 차이 7도, 단일 얼굴과 완성 기준 조건을 유지합니다. 등록을 쉽게 끝내려고 동일인·품질 조건을 없애지 않았습니다.

• 첫 샘플 대기·확보, 더 움직이기·정면 쪽 복귀, 과도한 기울임·선명도 부족 등 상태에 맞는 안내를 화면에 전달합니다.

### 발표 예시 약 45초

“아래 방향 등록이 멈춰 처음에는 얼굴 검출 문제로 보였습니다. 하지만 얼굴이 검출돼도 샘플 수집 조건을 통과하지 못하는 경로가 있었습니다. 0.2초 분석 주기보다 수집 대기가 길어 움직이는 중간 각도를 놓쳤고, 같은 깊은 각도만 남으면 다양성 조건을 만족하지 못했습니다. 정면 복귀와 특징 수집을 나누고 새로운 각도만 다음 분석에서 받을 수 있게 수정했습니다. 품질 기준을 낮추는 대신 상태와 시간 조건을 분리했습니다.”

### 두 사례를 묶은 배운 점

TLS에서는 “포트 연결”과 “암호화 인증”을, 등록에서는 “얼굴 검출”과 “유효한 샘플 수집”을 분리했습니다. 공통적으로 눈에 보이는 앞 단계의 성공만으로 전체 성공을 판단하지 않고, 다음 단계가 요구하는 조건과 상태를 확인했습니다. 앞으로도 각 단계의 입력·출력·실패 사유·시간을 기록하고, 재현 가능한 입력을 회귀 검사로 남기는 방식으로 문제를 해결하겠습니다.

### 현장 재확인 순서

• TLS  같은 Windows 계정에서 서버 실행 → 연결 코드 적용 → 인증 수신 → 직원 조회 → 영상 → 판정 응답 확인

• 등록  정면·좌우·위아래를 안내대로 수집하고 정체 시 화면 안내·각도·선명도·샘플 수를 함께 기록

• 발표  현재 문서의 코드·합성 검증과 사용자가 이전에 수행한 실장치 확인을 구분해서 설명
