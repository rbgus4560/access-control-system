# 출입관제 핵심 기술 발표 원고

핵심 기술 두 장에 사용할 문구와 발표 설명입니다. 기술 이름을 나열하기보다, 어떤 데이터를 어떤 방식으로 처리해 무엇을 구현했는지 설명합니다. AI는 직원을 식별하고 서버는 현재 출입 권한을 판정합니다.

### 보여줄 역량

WPF 앱과 Python 얼굴인식 AI를 연결하고, 클라이언트와 서버 사이에서 얼굴 기준·식별 결과·영상을 교환해 실제 출입 판정까지 이어지는 시스템을 구현한 역량입니다. DB는 이 흐름을 뒷받침하는 저장·조회 수단으로 설명합니다.

### 핵심 기술 슬라이드 구성

• 1장  TCP/IP를 사용한 클라이언트 서버 연결 — 기준 동기화, 식별 관측 전달, 서버 판정 응답과 영상 전송

• 2장  AI를 사용한 얼굴 판별 — 얼굴 검출·정렬·특징 추출·등록 직원 비교와 다방향 등록

• 문제 해결과 배운 점은 별도 한 장에 두 사례를 배치합니다. 상세 설명은 발표 노트로 사용합니다.

### 발표에서 구분할 것

• 직접 구현한 부분  앱 간 연결과 메시지, AI 호출·상태 관리, 얼굴 등록·동기화, 서버 권한 검증, 화면 표시

• 기존 기술 활용 부분  ArcFace 사전 학습 모델, DeepFace, dlib, MediaPipe, .NET 네트워크·암호화 API

• 새 모델을 직접 학습했다거나 인식 정확도·처리 속도를 측정했다고 표현하지 않습니다. 9분할 화면을 9대 동시 수신 검증으로 설명하지 않습니다.

## 핵심 기술 1 TCP/IP로 무엇을 구현했는가

### 슬라이드 제목

TCP/IP 통신으로 얼굴 식별과 서버 출입 판정을 연결

### 슬라이드에 넣을 문구

• 연결  C# 비동기 TCP 통신에 TLS 암호화와 연결 코드 검증 적용

• 데이터  등록 얼굴 특징 동기화 · 직원 식별 결과 전송 · 출입 허가·거부 응답

• 판정  서버가 현재 직원 상태와 출입 권한을 확인하고 결과 반환

• 영상  인증 데이터와 별도 채널로 실시간 JPEG 전송 · 녹화 구간 요청과 조회

### 그림에 넣을 한 줄 흐름

서버 → 얼굴 기준 동기화 → 클라이언트 AI 식별 → 서버에 관측 전송 → 권한 확인 → 클라이언트 결과 표시

### 실제 구현 순서

• 서버의 연결 코드에 서버 주소·제어 포트·연결 토큰·인증서 지문을 담습니다. 클라이언트가 이를 적용해 연결 대상을 설정합니다.

• TcpClient/TcpListener로 연결하고 SslStream으로 TLS 인증을 수행합니다. 인증서 유효기간·지문을 확인한 후 채널 이름과 토큰을 교환합니다.

• JSON 데이터 앞에 4바이트 길이를 붙입니다. 수신자는 먼저 길이를 읽고 지정한 바이트 수를 모두 읽어 한 메시지로 복원합니다.

• 얼굴 기준은 서버에서 받아 검증한 완성본을 AI에 적용합니다. 오래되거나 불완전한 기준을 그대로 식별에 쓰지 않도록 합니다.

• 클라이언트는 AI 일치 정보와 분석 상태 등 관측을 전송합니다. 서버는 DB의 현재 직원·등록·권한 상태와 정책을 확인합니다.

• 판정 결과와 사유를 클라이언트에 돌려주고 UI에 표시합니다. 서버는 영상을 받아 관제 화면에 표시합니다.

### 채널을 나눈 방식

기본 제어 포트를 P라고 하면, 관측·판정은 P, 실시간 영상은 P+1, 원격 API는 P+2를 사용합니다. 기본값 5050이면 5050·5051·5052입니다. 같은 PC의 등록 앱과 서버는 Named Pipe API를 사용하며, WPF와 Python AI는 별도 프로세스의 표준 입출력으로 연결합니다. 모든 연결을 TCP/IP라고 설명하지 않습니다.

## 핵심 기술 1 발표 설명과 근거

### 발표 예시 약 60초

“클라이언트와 서버를 TCP/IP로 연결해 얼굴인식 결과를 실제 출입 판정으로 이어지게 했습니다. 서버에 등록한 얼굴 특징을 클라이언트가 받아 AI 비교에 사용하고, 직원을 식별하면 그 결과와 분석 상태를 서버로 보냅니다. 서버는 얼굴 일치 여부에 더해 현재 직원 상태와 출입 권한을 확인한 뒤 허가 또는 거부를 반환합니다. 통신에는 TLS를 적용하고, TCP에서는 데이터가 나뉘어 도착할 수 있기 때문에 길이 정보를 붙여 메시지를 복원했습니다. 영상은 별도 채널로 보내 관제 화면에서 확인하도록 했습니다.”

### 이 구현에서 설명할 가치

• 단순 접속 성공을 넘어 요청·응답과 데이터 경계를 정의했습니다.

• 직원 식별과 권한 판정을 분리해, 얼굴이 일치하더라도 권한이 해제된 직원은 서버에서 거부합니다.

• 비동기 I/O와 취소 처리를 통해 UI와 통신 수명을 관리합니다. 비동기라는 이유만으로 무조건 빠르다고 주장하지 않습니다.

• TCP는 순서 있는 바이트 전달을 제공하지만 한 번의 읽기가 한 번의 전송 메시지와 같지는 않습니다. 길이 접두부가 필요한 이유입니다.

### 예상 질문

• TCP/IP와 TLS가 같은가요?  아닙니다. TCP/IP는 통신 기반이고 TLS는 그 위에서 암호화와 상대 확인을 제공합니다.

• 왜 DB에 직접 연결하지 않나요?  직원·권한의 원본과 판정 책임을 서버에 모으기 위해서입니다.

• TLS가 항상 적용되나요?  연결 프로필이 있는 실제 페어링 경로에서 적용합니다. 코드에는 프로필이 없을 때의 스트림 경로도 있어, 모든 테스트·로컬 통신이 TLS라고 단정하지 않습니다.

## 핵심 기술 2 AI로 무엇을 구현했는가

### 슬라이드 제목

얼굴을 특징 벡터로 바꾸고 등록 직원과 비교해 식별

### 슬라이드에 넣을 문구

• 입력 처리  dlib 얼굴 검출·눈 기준 정렬, MediaPipe 자세 추정

• 특징 추출  DeepFace를 통해 기존 ArcFace 모델로 512차원 얼굴 특징 생성

• 직원 식별  등록 얼굴 특징과 코사인 거리 비교 후 직원 후보 결정

• 앱 연동  WPF가 Python AI를 실행하고 분석 결과·등록 상태를 화면에 반영

### 등록과 인증을 나누어 설명

등록할 때는 직원 선택 → 얼굴 검출·정렬 → 자세·품질 확인 → 여러 방향 특징 확보 → 완성본 저장 → 클라이언트 동기화를 수행합니다. 인증할 때는 현재 얼굴 검출·정렬 → 특징 추출 → 직원별 등록 기준과 비교 → 후보 및 일치 여부 반환을 수행합니다. 이후 출입 권한은 서버가 확인합니다.

### 다방향 등록을 구현한 방법

• 안내형 등록은 정면 1개와 왼쪽·오른쪽·위·아래 방향의 대표 특징 각 2개로 총 9개를 완성합니다. 기존 5방향 기준도 읽는 호환 코드가 있습니다.

• 선명도, 얼굴 수, 방향, 각도 차이와 정면 특징과의 거리 등을 확인합니다. 같은 각도의 복사본 두 개만 모아 완료하지 않습니다.

• 수집 중인 pending 기준과 활성 기준을 분리합니다. 취소되거나 일부만 수집되면 기존 완성 기준을 불완전한 기준으로 바꾸지 않습니다.

• 다방향 수집은 자세 변화에 대응할 기준을 확보하려는 설계입니다. 실제 정확도가 몇 퍼센트 개선됐다는 근거는 없습니다.

### 식별 후에도 서버가 필요한 이유

AI의 “이 직원과 닮았다”는 결과와 “이 직원이 지금 출입해도 된다”는 업무 판단은 다릅니다. 퇴사·비활성·권한 해제 상태를 서버에서 확인하므로 얼굴 식별만으로 허가하지 않습니다.

## 핵심 기술 2 발표 설명과 근거

### 발표 예시 약 60초

“얼굴 사진을 그대로 비교하는 대신 AI가 추출한 특징 데이터를 비교했습니다. 먼저 dlib로 얼굴을 찾고 눈 위치를 기준으로 정렬합니다. MediaPipe로 고개 방향을 확인하면서 등록에 필요한 여러 방향 샘플을 수집하고, ArcFace로 얼굴을 512개의 숫자로 표현합니다. 인증할 때도 같은 과정을 거쳐 등록된 직원 기준과 코사인 거리를 비교해 후보를 찾습니다. 이 AI 결과를 WPF 화면과 서버 통신에 연결했고, 최종 출입 허용 여부는 서버가 판단하도록 했습니다.”

### 발표에서 말할 구현 기여

• 기존 모델을 앱의 등록·인증 과정에서 호출하고, 결과를 직원 정보·서버 판정과 연결했습니다.

• 검출 성공, 자세 적합, 샘플 수집, 특징 비교, 권한 허가를 서로 다른 상태로 다뤘습니다.

• Python AI와 WPF 사이에 명령·분석 결과를 주고받고, 최신 분석 상태를 화면에 반영합니다.

• 조명·자세·가림·유사 얼굴과 같은 실제 입력 조건에 대한 성능 측정은 별도 과제입니다.

### 검증 범위

이번 작성에서는 소스와 기존 문제 기록을 대조했습니다. .NET 앱 빌드와 얼굴 기준 계약 검사는 별도 실행 기록에 남깁니다. 실제 카메라 인식률, 여러 PC의 동시 수신 성능, 스푸핑 방어 능력을 이 문서가 입증하지는 않습니다.
