# 출입관제 사용 기술 이해하기

발표자가 기술 이름과 구현을 연결해 이해하기 위한 해설입니다. 슬라이드에 모두 옮기지 않고, 질문에 답할 때 참고합니다.

### 전체 흐름부터 이해하기

관리자가 직원 얼굴을 등록하면 AI가 얼굴 특징을 숫자 데이터로 만듭니다. 서버가 이를 저장하고 클라이언트에 전달합니다. 출입구에서 새로운 얼굴이 들어오면 클라이언트 AI가 등록 직원과 비교하고, 서버는 그 직원의 현재 권한을 확인해 결과를 반환합니다.

### WPF와 C#

WPF는 Windows 데스크톱 화면을 만드는 UI 기술입니다. XAML로 화면을 구성하고 C#에서 버튼·상태·통신 결과를 처리합니다. 이 프로젝트의 등록 화면, 인증 화면, 관제 화면이 WPF입니다. WPF 자체가 얼굴을 판별하는 것은 아닙니다.

### IP와 포트와 TCP

• IP 주소는 상대 컴퓨터를 찾아가는 주소입니다. 포트는 그 컴퓨터 안에서 어떤 프로그램의 통신 창구로 들어갈지 정하는 번호입니다.

• TCP는 연결을 맺고 바이트를 순서대로 전달하는 통신 방식입니다. 보내는 데이터가 여러 조각으로 도착하거나 연속으로 붙을 수 있습니다.

• 프로젝트에서는 제어·영상·원격 API 통로를 구분했습니다. 포트가 열렸다는 사실만으로 TLS·앱 인증·권한 판정까지 성공했다는 뜻은 아닙니다.

### 길이 접두부와 JSON

JSON은 직원 ID나 결과처럼 이름과 값을 갖는 데이터를 표현하는 형식입니다. 프로젝트는 JSON 바이트 앞에 4바이트 길이를 붙입니다. 예를 들어 본문이 120바이트이면 먼저 120이라는 길이를 전송하고 본문을 전송합니다. 수신자는 4바이트를 읽어 길이를 알고, 그다음 정확히 120바이트를 모아 해석합니다. 이는 TCP의 바이트 흐름에 앱 메시지 경계를 만드는 방법입니다.

## 암호화와 프로세스 연결 이해하기

### TLS와 인증서 지문

TLS는 TCP 위에서 통신 내용을 암호화하고 상대를 확인하는 계층입니다. 인증서는 서버의 공개키 정보를 담고, 서버는 대응하는 개인 키를 TLS 인증에 사용합니다. 프로젝트는 서버 인증서의 SHA-256 지문을 연결 코드에 담아, 접속한 인증서가 예상한 서버의 것인지 비교합니다. 연결 토큰은 추가적인 앱 연결 확인에 사용합니다.

### 개인 키와 PFX와 Schannel

• 개인 키는 서버가 자신임을 증명할 때 필요한 비밀 키입니다. 인증서 파일이 존재해도 개인 키를 TLS 제공자가 사용하지 못하면 인증이 실패할 수 있습니다.

• PFX는 인증서와 개인 키 등을 담을 수 있는 묶음 형식입니다. Windows에서는 .NET의 TLS 구현이 운영체제 보안 제공자인 Schannel과 연동합니다.

• EphemeralKeySet은 일시적인 키 로딩 방식이며, UserKeySet은 사용자 키 영역을 사용합니다. 이 프로젝트는 Windows에서 Schannel이 사용할 수 있도록 UserKeySet으로 로딩하고 HasPrivateKey를 검사합니다. 모든 Windows TLS 실패가 이 원인이라는 뜻은 아닙니다.

### 비동기 처리와 취소 토큰

await를 사용한 비동기 I/O는 데이터가 도착하기를 기다리는 동안 UI 스레드를 붙잡지 않도록 구성하는 방법입니다. CancellationToken은 창 종료나 연결 해제 시 대기 작업을 끝내는 데 사용합니다. 비동기는 곧 AI 연산이 빨라진다는 의미가 아닙니다.

### Named Pipe와 표준 입출력

Named Pipe는 같은 PC의 프로그램끼리 데이터를 주고받는 통로입니다. 등록 앱과 서버의 로컬 API에서 사용합니다. 표준 입력과 표준 출력은 부모 앱과 Python 프로세스 사이 명령·결과 전달에 사용합니다. 원격 클라이언트 서버 연결과 로컬 프로세스 연결을 구분하면 구성도를 설명하기 쉽습니다.

### 공식 근거

Microsoft SslStream 인증 문제 해결: https://learn.microsoft.com/en-us/dotnet/core/extensions/sslstream-troubleshooting — Windows의 일시적 개인 키 사용 문제를 설명합니다. 프로젝트에 적용한 근거는 Shared/PairingStore.cs와 Network/SecureLink.cs입니다.

## 얼굴 AI의 단계 이해하기

### 검출과 정렬과 자세 추정

• 얼굴 검출은 영상에서 얼굴이 어디 있는지 찾는 단계입니다. “사람이 누구인지”는 아직 모릅니다. dlib 검출기를 사용합니다.

• 정렬은 눈 등의 위치를 기준으로 얼굴 입력의 기울기와 배치를 맞추는 단계입니다. 비교할 얼굴의 입력 조건을 맞추려는 전처리입니다.

• MediaPipe 얼굴 랜드마크는 얼굴의 특징점 위치를 제공합니다. 이 정보를 자세 추정에 이용합니다. pitch는 위아래, yaw는 좌우, roll은 옆으로 기울어진 정도를 뜻합니다. 실제 부호와 안내 문구는 구현 기준을 따라야 합니다.

### ArcFace와 DeepFace와 512차원

ArcFace는 얼굴을 비교 가능한 특징으로 표현하는 얼굴인식 모델입니다. DeepFace는 여러 얼굴인식 모델을 호출할 수 있게 하는 라이브러리이며, 이 프로젝트는 model_name="ArcFace"를 사용합니다. 512차원은 얼굴 특징을 512개 숫자로 표현한다는 뜻이지, 512명의 직원을 등록한다는 뜻이 아닙니다. 모델을 새로 학습한 것이 아니라 기존 가중치로 추론합니다.

### 코사인 거리와 임계값

특징 벡터의 방향이 비슷한지 비교합니다. 코사인 거리는 1 − (A·B)/(‖A‖‖B‖)이며, 작을수록 비슷한 특징입니다. 벡터를 단위 길이로 정규화하면 내적을 사용해 계산할 수 있습니다. 프로젝트는 직원별 여러 등록 특징과의 거리를 구해 후보를 비교합니다. 거리는 확률이나 정확도가 아닙니다. 0.2를 “80% 정확도”로 바꾸면 안 됩니다.

기본 인식 거리 설정과 등록 도중 정면 얼굴과 비교하는 동일인 검사 기준은 목적이 다릅니다. 예를 들어 브리지 초기 인식 설정의 0.45와 안내형 등록의 0.60은 서로 바꿔 쓰는 숫자가 아닙니다. 실제 실행에서는 설정·정책과 함께 해석해야 하며, 임계값의 최적성은 별도 데이터 평가가 필요합니다.

### 기술별 담당 역할

• OpenCV  카메라 프레임·이미지 처리 및 영상 저장 관련 기능

• dlib  얼굴 검출과 눈 위치 기반 정렬

• MediaPipe  얼굴 랜드마크와 자세 추정 입력

• DeepFace와 ArcFace  얼굴 특징 벡터 추출

• NumPy  벡터 정규화·거리 계산

• C#과 WPF  UI·AI 프로세스·서버 통신 연결

## 샘플 수집과 확인할 질문

### 왜 여러 방향을 등록하는가

출입자는 항상 같은 정면 자세로 서 있지 않습니다. 여러 방향의 특징을 기준으로 준비하는 것이 설계 의도입니다. 안내형 등록은 정면과 각 방향의 서로 다른 대표 시점을 모읍니다. 다만 이 의도만으로 인식률 향상을 수치로 주장할 수는 없습니다.

### 쿨다운과 각도 다양성

쿨다운은 연속 수집 사이에 두는 최소 대기 시간입니다. 같은 프레임을 반복 수집하거나 비싼 특징 추출을 너무 자주 하는 것을 제한합니다. 각도 다양성은 같은 방향에서도 서로 다른 시점을 확보하는 조건입니다. 대기 시간이 너무 길면 움직이는 중간 각도를 놓쳐 두 조건이 충돌할 수 있습니다.

### 세 가지 성공을 구분하기

• 검출 성공  영상에 얼굴이 보임

• 식별 성공  등록된 직원 특징과 일치 조건을 만족함

• 출입 허가  서버의 현재 직원 상태와 출입 권한까지 허용됨

### 자주 받는 질문과 답변

• 왜 얼굴이 보이는데 등록이 안 되나요?  얼굴 검출 외에 현재 안내 방향, 선명도, 각도 차이, 수집 간격 등 조건도 만족해야 합니다.

• 얼굴이 같으면 항상 허가되나요?  아닙니다. 서버에서 권한을 해제했거나 직원이 비활성이면 거부됩니다.

• 사진으로 인증하는 공격도 막나요?  이 설명만으로 실제 생체 여부 검증을 구현했다고 주장하지 않습니다.

• DB가 핵심 기술인가요?  이번 발표의 중심은 AI 적용과 클라이언트 서버 통합이며 DB는 기준·권한·이력을 유지하는 보조 역할입니다.
