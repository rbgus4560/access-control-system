# 11.1 · 메뉴별 별도 창 · .NET 10 / WPF UI

메인은 카메라·출입 결과·간단한 연결 상태·최근 인증·24시간 타임라인을 중심으로 정리했다. 사용자 목록·사용자 등록·설정·최근 기록 영상은 각각 별도 창으로 연다. 설정 창을 닫아도 카메라·AI·녹화는 유지된다.

서버·인증·등록 종료 후 덮어쓰기, Start_Net10.cmd 실행. SQL 재실행·모델 설치·얼굴 재등록은 필요 없다. 서버도 11.1로 업데이트한다. 인증 앱의 설정에서 서버/카메라 연결, 사용자 목록에서 직원 선택·얼굴 불러오기를 진행한다. 세부 절차는 ../validation/VALIDATION_STAGE12_1_WINDOWS.md.

# 10.6 원본 녹화 자동 정리 · .NET 10

세 앱 종료 후 덮어쓰기, Start_Net10.cmd 실행. 인증 앱 왼쪽에 원본 보관 72시간 표시를 확인한다. 구간 종료 후 72시간이 지난 완료 원본을 정리하고 삭제 메타데이터를 DB로 동기화한다. 재생·클립 추출 사용 중 원본은 보류하며 클립은 보관한다. 현재 어제·오늘 영상은 아직 만료 대상이 아닐 수 있다.

# .NET 10 전환본 10.5-net10

2026-10-19. .NET 10으로 대상 버전과 실행 경로를 변경했다. Windows 실제 동작은 아래 순서로 확인한다.

1. 기존 10.5 폴더 백업 및 세 앱 종료.
2. 이 ZIP의 AccessControl_UI 안 내용을 기존 AccessControl_UI에 덮어쓰기.
3. Start_Net10.cmd 실행. 세 WPF 앱을 빌드한 뒤 서버·인증 창을 연다.
4. 창 제목의 .NET 10 확인. 서버 DB 연결·관리자 선택·TCP 시작.
5. 인증 앱 서버 연결, 등록 직원 조회·얼굴 불러오기, 카메라·AI 연결.
6. 본인 비교·허가/거부·서버 영상·녹화·재생·클립 순서로 확인.

얼굴 DB·모델·Conda 환경을 다시 만들거나 SQL 생성문을 재실행할 필요는 없다. 기능과 모델·Npgsql 버전은 이번 전환에서 유지했다. 기존 bin\Debug\net8.0-windows에 남은 EXE를 직접 실행하지 않는다. 새 경로는 net10.0-windows다. 새 시작 스크립트도 수정된 경로를 사용한다.

4. 현재 출입 기록 연결이 켜졌다면 기록 시각이 이 범위 안인지 확인하거나 연결을 해제한다.
5. MP4 클립 추출 후 추출·DB 기록 완료 메시지 확인. 완료 파일 재생으로 약 5초 MP4 확인.

기존 녹화를 사용하므로 새 촬영·얼굴 등록·SQL 재실행·모델 설치가 필요 없다. 같은 날짜 최대 5분 범위를 지원한다. 범위에 녹화가 없으면 추출을 거절한다.

## 저장·오류 처리

- 별도 OpenCV Python 프로세스에서 원본 필요한 프레임을 읽고 mp4v 10fps 클립 생성. 여러 녹화 파일을 하나로 합친다. 원본은 유지한다.
- `%LOCALAPPDATA%\AccessControlSystem\clips` 폴더에 GUID 이름 MP4, 결과 JSON, .job.json 저장. 클립 폴더 열기로 접근한다.
- 기존 exported_clips에 담당 관리자·선택 이벤트·범위·경로·EXPORTING/READY/FAILED·크기·SHA256·완료시각 기록.
- MP4 완료 후 DB 반영이 실패하면 파일·결과를 보관하고 자동 재시도한다. 동기화 대기를 완료로 표시하지 않는다.
- 출력 전 여유 공간 20GB 기준 확인. 실제 녹화 공백이나 큰 시간 오차는 거절한다. 출력 길이는 10fps 프레임 단위이며 완료 메시지에 표시한다.
- PC 전원 차단 등으로 남은 EXPORTING 이력의 자동 복구, 오래된 원본 자동 정리는 아직 후속 범위다.

세 WPF 빌드, 기존 계약·권한·영상 TCP 검사, 클립 프레임 범위 검사, 실제 Linux OpenCV 테스트 MP4 추출 검사를 통과했다. 실제 사용자 Windows에서 MP4 생성·재생과 DB 반영은 적용 후 확인한다. 상세 ../validation/VALIDATION_STAGE10_5.md, 읽기 전용 DB 확인 Database/11_verify_exported_clips.sql.

10-4 기록 선택 후 해당 영상 열기는 사용자 PC에서 확인했다. 이후 남은 통합 검증·보관 정책·UI 라이브러리 적용·회전 기반 연속 얼굴 등록은 NEXT_DEVELOPMENT.md의 후속 범위다.

# AccessControlSystem — 10-4 출입 기록 시각 재생 10.4

## 바로 확인

1. 기존 세 앱 종료, ZIP 내용을 기존 폴더에 덮어쓰기, Start_Stage10.cmd 실행. 서버·인증 창 10.4 확인.
2. 서버에서 DB 연결 및 목록 조회를 누른다.
3. 출입 기록에서 녹화 시간 범위 안의 행을 선택한다. 예: 15:49:07 기록은 기존 15:48:58.402~15:49:38.802 녹화 범위에 포함된다.
4. 선택 기록 영상 버튼 또는 행 더블클릭. 인증 앱에서 해당 시각 PLAYBACK과 기록 설명을 확인한다.
5. LIVE로 복귀한다. 녹화 없는 시각의 기록은 녹화 없음 안내를 확인한다.

카메라를 새로 열 필요 없이 기존 파일과 DB 기록으로 확인할 수 있다. 새 SQL·모델 설치·얼굴 재등록은 없다.

이벤트 ID로 DB 원본 시각을 다시 읽어 인증 앱에 전달한다. 화면의 초 단위 문자열로 재생 위치를 계산하지 않는다. 로컬 사용자 전용 파이프를 사용하고, 요청 시간·ID·카메라·메시지 크기를 검증한다. 응답은 파일 열기 요청 처리 결과이며 실제 영상 재생은 PLAYBACK 화면으로 확인한다.

세 WPF 프로젝트 빌드·이벤트 요청 검사·기존 권한/영상 통신 검사를 통과했다. 실제 DB 이벤트 조회·Windows 파이프·화면 전환은 적용 후 확인한다. 상세는 ../validation/VALIDATION_STAGE10_4.md.

10-3 앱 내부 영상 재생은 사용자 PC에서 확인했다. 직접 시각 입력·LIVE 복귀는 추가 확인 항목이다. 다음은 10-5 MP4 클립 추출이다. 보관 정책·UI 라이브러리·연속 얼굴 등록은 NEXT_DEVELOPMENT.md에 기록한 후속 범위다.

- 카메라 중지·영상 지연 시 이전 이미지를 지운다. 카메라 재연결 및 서버 TCP 중지·시작 뒤 영상도 자동 재접속한다.
- 서버 영상은 실시간 카메라 화면이며 마지막 AI 분석 프레임이 아니다. 영상과 오른쪽 출입 판정은 각자의 최신 상태로 갱신된다.
- 실시간 영상이 나온다는 사실만으로 얼굴 인증이 완료되거나 출입이 허용되지는 않는다. 출입 판정은 기존 DB 권한·분석 최신성 검사를 따른다.

# AccessControlSystem — 9단계 권한 판정·DB 출입 기록 9.0

## 적용 및 첫 실행

1. 기존 서버·인증·등록 앱을 모두 종료한다. 8단계에서 저장한 얼굴은 DB에 남으므로 재촬영하지 않는다.
2. ZIP의 AccessControl_UI 내용을 기존 솔루션 폴더에 덮어쓴다. Network·FaceService·Shared 및 세 프로젝트를 함께 적용한다.

5. 인증 앱에서 서버 연결을 누른다. 등록 직원 조회에서 0511 직원을 선택하고 선택 직원 얼굴 불러오기를 누른다.

새 DDL은 없다. 기존 SQL을 재실행하거나 DB를 초기화하지 않는다. 기존 등록 데이터의 Windows DPAPI 형식과 모델 버전은 그대로 유지한다. 통신 응답이 추가돼 TCP 프로토콜은 Version=2다. 이전 7.0/8.0 인증 앱과 9.0 서버를 혼용하지 않는다.

## 허가·거부 검사

### 출입 권한이 꺼진 직원

얼굴이 일치해도 출입 거부 (DENIED)와 직원 출입 권한 없음이 표시돼야 한다. 서버 DB 기록에 ACCESS_DISABLED 사유가 남는다.

### 출입 권한 허용

서버의 직원 관리에서 0511 직원을 조회·선택하고 활성 상태를 유지한 채 출입 허용을 체크해 변경사항을 저장한다. 다음 인증 응답에서 출입 허가 (GRANTED) 및 ACCESS_ALLOWED 기록이 나와야 한다. 이때 서버 DB 연결 버튼을 다시 누를 필요가 없다. 직원 관리 창을 닫고 결과를 확인한다.

### 출입 권한을 다시 해제

같은 직원의 출입 허용을 해제하고 저장하면 다시 DENIED여야 한다. 권한 변경 버전이 달라져 새 기록으로 구분한다. 직원 활성 자체를 끄면 PERSON_INACTIVE로 거부한다. 비활성 직원의 새 DB 기준 불러오기는 8단계 정책대로 거절한다.

### 다른 얼굴·얼굴 이탈·여러 얼굴

새 분석의 얼굴 불일치는 NO_MATCH로 거부하고 person_id/enrollment_id를 NULL로 저장한다. 이를 선택 직원의 신원으로 기록하지 않는다. 얼굴 없음·여러 얼굴·명령 처리·분석 지연·비교 꺼짐은 판정 대기이며 새 출입 이벤트를 만들지 않는다.

### 기록 보존과 중복 방지

한 얼굴과 같은 권한 상태를 유지할 때 같은 기록이 매초 늘어나면 안 된다. 비교가 2초 이상 중단된 뒤 다시 비교되거나 비교 대상/결과가 바뀌면 새 인증 시도로 구분한다. 매우 짧은 분석 품질 저하는 같은 시도로 유지한다.

TCP 중지·재시작 후 같은 인증 시도의 재전송은 같은 이벤트 ID를 사용한다. 직원·장치 정보의 DB 변경 버전이 달라지면 같은 시도 중에도 새 정책 판정을 별도로 기록한다. 같은 이벤트 ID의 재전송은 INSERT ON CONFLICT DO NOTHING으로 중복 저장하지 않는다.

서버의 출입 기록 조회를 눌러 DB의 최근 최대 500건을 읽는다. 두 앱을 종료하고 다시 켠 다음 서버 DB 연결을 해도 이력이 남아 있어야 한다.

## 판정 근거와 저장 규칙

- 서버는 매 응답에서 DB의 직원 활성·출입 허용, 얼굴 등록 활성·모델, 인증 카메라와 클라이언트 사용 허용을 확인한다. 얼굴 일치만으로 GRANTED를 만들지 않는다.
- DB 얼굴 불러오기 시 서버가 발급한 메모리 식별 정보와 직원/등록 ID를 연결한다. 임시 Named Pipe 기준을 덮어쓰거나 초기화하면 기존 DB 신원 연결을 해제한다. 표시 이름으로 권한을 찾지 않는다.
- 같은 PC의 TCP 127.0.0.1:5050을 사용한다. 얼굴 특징은 기존 사용자 전용 로컬 DB 요청 파이프로만 전달하며, TCP에는 상태·식별 정보·판정 응답을 보낸다.
- 발신 시각·분석 나이·현재 인증 시도를 확인한다. 오래되거나 이미 다른 시도로 바뀐 권한 응답은 현재 출입 허가로 표시하지 않는다.
- DB 행 잠금으로 판정 중 직원/등록/장치 상태의 변경을 제어하고, 출입 기록 트랜잭션이 완료된 뒤 GRANTED를 응답한다. DB 미연결·쿼리 실패·시간 초과는 허가로 바꾸지 않는다. DB 장애 자체를 같은 DB에 기록했다고 보장하지 않는다.
- 서버를 완전히 종료하거나 DB 연결을 새로 만들면 메모리의 기준 발급 정보가 초기화된다. 이때 인증 앱에서 DB 얼굴 기준을 다시 불러온다. 얼굴 재촬영은 필요 없다. TCP 서버 중지/시작만으로는 이 정보를 초기화하지 않는다.
- DB access_events.similarity는 코사인 유사도(1-거리), threshold는 유사도 기준 0.550을 저장한다. 화면은 거리와 거리 기준 0.450을 표시한다. Database/09_verify_access_events.sql에서 같은 단위로 변환해 확인할 수 있다.

# AccessControlSystem — 8단계 직원·얼굴 DB 연결 8.0

## 적용과 서버 준비

1. 기존 등록·인증·서버 창을 모두 닫는다. 진행 중인 얼굴은 메모리에만 있으므로 종료 전에 필요한 작업을 마친다.
2. ZIP의 AccessControl_UI 내용을 기존 솔루션 폴더에 덮어쓴다. 새 FaceService 폴더도 포함한다. 가상환경·모델 캐시·기존 PostgreSQL DB는 유지한다.
3. Start_Stage8.cmd를 더블클릭한다. 세 프로젝트를 빌드하고 서버 및 인증 앱을 연다. 창 제목에서 직원·얼굴 DB 8.0을 확인한다.
4. 서버에서 DB 비밀번호를 입력하고 DB 연결 및 목록 조회를 누른다. 기본 access_control_system / postgres / 127.0.0.1:5432다. 성공하면 직원·얼굴 요청을 처리할 준비가 된다. DB 연결 비밀번호는 서버가 열려 있는 동안 메모리에만 보관한다.
5. 얼굴 등록 관리자 목록을 확인한다. 기존 관리자가 있으면 선택한다. 비어 있다면 관리자 추가에서 ID·이름·10자 이상 비밀번호를 한 번 등록한다. 이는 얼굴 등록 이력의 등록 담당자다. DB 접속 비밀번호와 별개이며 비밀번호 원문은 저장하지 않는다.
6. TCP 서버 시작 및 인증 앱 서버 연결을 누른다. 상태 전송은 기존 5050 포트를 사용한다.

기존 SQL을 다시 실행하거나 테이블을 새로 만들 필요가 없다. 서버의 표시 초기화는 직원·얼굴 요청 서비스를 미연결로 되돌리므로 다시 DB 연결을 해야 한다. 서버 종료 후에도 DB의 직원·얼굴 특징은 남아 있고, 새로 실행하면 DB 연결과 관리자 선택을 다시 한다.

## 직원과 얼굴 등록

1. 직원이 없으면 서버의 직원 관리에서 먼저 등록한다. 비활성 직원에게는 얼굴을 등록할 수 없다.
2. 인증 앱의 사용자 등록으로 등록 앱을 연다.
3. 등록 앱에서 DB 직원 조회를 누르고 대상 직원을 선택한다. 선택한 사원번호와 이름은 직접 수정할 수 없으며, DB 저장 대상은 선택한 직원 ID다.
4. 단일 카메라는 인증 앱에서 연결하지 않고 등록 앱의 카메라 0을 사용한다. 정면 보정, 5방향 등록 시작, 정면·위·아래·왼쪽·오른쪽 촬영을 완료한다.
5. 선택 직원 얼굴 DB 저장을 누른다. 성공 안내의 사원번호·이름과 5/5를 확인한다. 기존 얼굴 등록이 있으면 교체 확인을 받으며 기존 이력은 삭제하지 않는다.
6. DB 저장 성공을 확인한 뒤 등록 앱의 연결 종료를 누르거나 등록 앱을 닫아 카메라를 넘긴다.

같은 등록 시도 도중 직원 목록이 오래돼 다른 얼굴 등록이 생긴 경우 저장을 거절한다. 다시 조회하고 의도한 직원을 선택한다. 저장 실패 안내가 나오면 창을 닫기 전에 서버 연결·관리자 선택을 확인한다. 응답이 끊겨 실제 저장 여부가 불명확하면 직원 목록을 다시 조회한다.

인증 앱으로 임시 기준 전달 버튼도 남아 있다. 이 버튼은 기존 6.5 메모리 전달이며 DB 저장을 수행하지 않는다. DB에 보관하려면 선택 직원 얼굴 DB 저장을 사용한다.

## DB에서 인증 기준 불러오기

1. 인증 앱 왼쪽 등록 직원 조회를 누른다. 활성 직원 중 얼굴 등록이 있는 직원만 표시한다.
2. 직원을 선택하고 선택 직원 얼굴 불러오기를 누른다. DB 기준 수신 5/5를 확인한다.
3. 카메라·AI를 연결한다. 정면 보정과 얼굴 비교 켜기를 진행한다. 인증 기준 5/5와 선택 직원 이름을 확인한다.
4. 본인 후보·타인 불일치 및 얼굴 없음·여러 얼굴에서 비교 중지를 확인한다. 서버에서도 비교 상태가 바뀌는지 확인한다.
5. 인증 앱을 종료하고 다시 켠다. 다시 등록하지 않고 등록 직원 조회 및 얼굴 불러오기로 같은 기준을 적용할 수 있는지 확인한다.

현재 한 번에 선택한 직원 한 명의 5방향 기준과 비교한다. 여러 직원 중 자동 신원 검색은 아직 구현하지 않았다. 출입 허가 판정·DB 이벤트 기록은 9단계에서 연결한다. 서버의 현재 수신 이력은 메모리 관찰 목록이다.

## 저장·통신 방식

- 기존 access_control.persons, admin_accounts, face_enrollments, face_templates를 사용한다.
- 얼굴 특징은 Windows DPAPI CurrentUser로 암호화한 BYTEA로 보관한다. 서버를 실행하는 같은 Windows 사용자 계정에서 복호화한다. 다른 PC나 Windows 계정으로 DB만 옮기면 그대로 읽을 수 없다.
- 다섯 방향의 각 512차원 특징과 모델·전처리 버전을 검증한다. DB 저장 트랜잭션이 완료돼야 새 묶음을 활성화한다. 기존 활성 묶음은 같은 트랜잭션에서 비활성화한다.
- 원본 얼굴 사진을 파일이나 DB에 저장하지 않는다. DB의 captured_at은 서버 저장 시점이며 카메라 촬영 원시 시각을 별도로 수집한 값은 아니다.
- 직원·얼굴 DB 요청은 같은 PC·같은 Windows 사용자 계정의 전용 Named Pipe를 통해 서버가 처리한다. 클라이언트에는 DB 비밀번호를 배포하지 않는다. 상태 관찰은 기존 TCP 5050으로 전송한다.
- 관리자 비밀번호는 임의 salt 및 PBKDF2-SHA256 210000회 해시로 저장한다. 현재 관리자는 등록 이력의 담당자이며, 별도 관리자 로그인 화면은 아직 연결하지 않았다.
- 비활성 직원 또는 비활성·호환되지 않는 등록은 불러오기를 거절한다. 불러오기 시작 시 이전 비교 기준을 지워 잘못된 이전 결과 표시를 방지한다.

빌드와 로직 검증은 ../validation/VALIDATION_STAGE8.md, DB 저장 결과 조회용 읽기 SQL은 Database/08_verify_face_storage.sql을 참고한다. 실제 Windows의 DPAPI·Named Pipe 및 사용자 DB 저장·재시작 복원은 적용 후 검증한다.

# AccessControlSystem — 7단계 TCP 연결 7.0

## 이번 버전 실행

1. 기존 등록·인증·서버 앱을 종료한다. 인증 앱에 임시 보관 중이던 얼굴 기준은 종료 시 사라진다.
2. ZIP의 AccessControl_UI 안에 있는 파일과 폴더를 기존 AccessControl_UI 폴더에 덮어쓴다. 새 Network 폴더도 함께 복사한다. AI 가상환경과 model_cache는 그대로 사용한다.
3. 솔루션 폴더의 Start_Stage7.cmd를 더블클릭한다. .NET SDK로 세 프로젝트를 빌드한 뒤 서버 앱과 인증 앱을 연다. 빌드 오류가 나면 명령창이 남으므로 오류를 확인한다.
4. 서버 앱의 TCP 서버 시작을 누른다. 기본 127.0.0.1:5050이다. PostgreSQL 5432와 다르다. DB 연결은 이번 TCP 검사에 필요하지 않다.
5. 인증 앱 왼쪽 서버 연결을 누른다. 수신 확인 #번호가 증가하고 서버에 RECOGNITION-01 / CAM-01 수신 횟수가 나오면 기본 연결 성공이다. 카메라 미연결이면 새 분석 결과 대기가 정상이다.
6. 서버 중지 후 다시 TCP 서버 시작을 눌러 인증 앱이 자동 재접속하는지 확인한다. 인증 앱의 서버 연결 종료를 누르면 자동 재접속도 멈춘다.

## 얼굴 결과 수신 검사

기존 6.5 방식으로 등록 앱에서 5/5를 촬영해 인증 앱에 전달한다. 한 대의 카메라는 등록 카메라를 해제한 뒤 인증 앱에서 연결한다. 정면 보정 후 얼굴 비교를 켠다.

- 본인 비교: 서버 등록 얼굴 일치 후보와 거리 표시
- 타인 비교: 서버 등록 얼굴 불일치 표시
- 얼굴 없음·두 명·비교 끄기: 서버 비교 대기/중지, 거리 숨김
- 분석 지연·명령 처리: 서버 새 분석 결과 대기, 이전 비교 숨김
- AI 연결 종료: 서버 대기 상태 전송
- TCP 응답 중단: 마지막 분석이 오래되면 일치 후보 숨김, 5초 통신 제한 후 연결 종료 표시

전송 주기는 약 1초다. 1초 간격 상태 수신이므로 아주 짧은 얼굴 상태 변화를 모두 수집하지는 않는다. 현재 목록은 상태 변경 시 메모리에 기록하며 최대 500건이다. DB 이벤트 이력이나 출입 허가 기록과는 구분한다.

## 완료 범위와 다음 단계

7.0은 동일 PC의 IPv4 루프백 TCP 연결, 응답 확인, 상태·얼굴 비교 결과 전송, 자동 재접속을 구현했다. 서버는 한 인증 앱을 순차 수신한다. 다른 PC 접속·서버 영상·녹화·권한 판정·얼굴 DB 저장은 아직 연결하지 않았다. Named Pipe 임시 얼굴 기준 전달은 기존 방식 그대로다. 얼굴 이미지·512차원 특징은 TCP에 전송하지 않는다.

내부 검증: 세 WPF 프로젝트 빌드와 실제 루프백 TCP 검사를 통과했다. Windows 화면과 카메라를 통한 결과 전송은 적용 후 확인한다. 검증 항목은 ../validation/VALIDATION_STAGE7.md, 테스트는 NetworkChecks/NetworkChecks.csproj에 있다.

다음은 8단계 직원과 얼굴 특징 DB 연결, 9단계 권한 판정과 DB 이벤트 기록이다. 기존 DB를 재생성하거나 초기 SQL을 다시 실행하지 않는다.

## 숙인 얼굴 검출 보완 6.4 — 2026-10-18

등록 2/5에서 아래 방향을 촬영할 때 얼굴 검출 대기가 표시됐습니다. 제공 화면의 Mesh·dlib 처리 시간으로 보아 dlib 검출 실패로 추정합니다. 실제 자세·조명에 대한 검증은 적용 후 확인해야 합니다.

- 480폭 HOG 검출 결과가 비어 있을 때만 같은 축소 이미지에 upsample=1 검출을 한 번 더 수행합니다. 원본 영상 패딩 영역을 검출하지 않으며, 정상 검출은 기존 빠른 경로를 유지합니다.

- 결과의 처리 시간에 detector_upsample=0 또는 1이 포함됩니다. 재검출 프레임의 분석 시간은 늘어날 수 있습니다. 실제 고개를 깊게 숙여 눈이 가려지는 상황에서 검출을 보장하지 않습니다.
- 적용: 앱을 종료하고 ZIP의 FaceAI 폴더 전체를 기존 FaceAI에 덮어씁니다. 다시 빌드할 필요가 없습니다. 진단에서 bridge 6.4를 확인합니다. 메모리에 있던 진행 중 2/5는 정면 보정과 정면 촬영부터 다시 시작합니다.

## 시작 대기 진단 6.2 — 2026-10-18

Windows에서 준비 중이 285초 지속되고 분석 수신이 0개인 현상에 대한 진단 패치입니다. 직접 Python 실행에서는 얼굴 분석이 정상적으로 반복됐습니다. 정확한 대기 호출은 아직 확인 전입니다.

이 패치는 원인 확인을 위한 변경입니다. Windows에서 멈춤이 해결됐는지는 아직 확인하지 않았습니다.

## 연결 보완 6.1

Python 단독 검사는 통과하지만 WPF에서 실시간 영상만 보이고 AI 준비 중에 머무는 증상에 대응한 버전입니다. 원인은 아직 Windows에서 확정하지 않았으며, 적용 후 실제 결과를 확인해야 합니다.

- WPF가 실행한 Python 프로세스 안에서 별도 AI 스레드가 모델과 등록 상태를 소유합니다. 카메라 획득과 AI 작업은 별도 루프이며, 영상·분석 대기열은 최신 1개만 유지합니다. WPF 화면은 별도 .NET 프로세스입니다.
- Windows Conda 환경의 네이티브 DLL 검색 경로를 Python 실행 시 추가합니다.
- 진단 보강: 실행 경로, Python PID, 모델 로딩 단계, 최초 분석 수신, 영상/분석 수신 개수 및 경과 시간. 영상 데이터와 얼굴 특징은 진단에 기록하지 않습니다.
- 설정 펼침 영역에 **연결 보완 6.1**이 보여야 최신 빌드입니다. 기존 실행 앱·터미널 카메라 검사를 종료하고 ZIP을 교체한 뒤 솔루션을 다시 빌드합니다. Visual Studio 실행 시에도 가상환경을 별도로 활성화할 필요가 없습니다.
- 분석이 나오지 않으면 진단 보기의 내용을 전달합니다. Windows 실카메라 확인과 두 앱 간 Named Pipe 전달 확인은 아직 남아 있습니다.

Python 연결 스크립트는 비교 진단용으로 `--worker-mode process` 옵션도 지원합니다. 기본 WPF 실행은 `thread`입니다. 기존 독립 Python 검증 프로그램 `face_check.py`의 작업 방식은 변경하지 않았습니다.

등록·인증 화면을 실제 카메라와 얼굴 AI에 연결한 프로젝트입니다.
서버의 기존 PostgreSQL 직원 등록·조회·수정 기능은 그대로 포함합니다.

- 왼쪽은 현재 영상, 오른쪽은 마지막 분석 영상입니다. 느린 AI 결과를 왼쪽 영상에 억지로 겹치지 않습니다.
- 비교 점수는 마지막 분석 영상에만 해당합니다. 현재 화면의 매 프레임 신원 판정이 아닙니다.
- 촬영 후 2.5초를 넘긴 결과와 아직 반영되지 않은 명령의 이전 결과는 숨깁니다.
- JPEG 영상 전송 상한은 25fps이고 실제 표시 속도는 카메라·PC·전송에 따라 달라집니다.
- 화면 아래 처리 시간은 Mesh / dlib 검출·정렬 / ArcFace / 전체의 ms입니다.
- 정면 보정·촬영·기준 전달·비교 켜기/끄기는 버튼으로 조작합니다. 기존 Python 창의 키 입력은 사용하지 않습니다.
- 세 앱은 각각 한 개씩 실행합니다. 인증 앱이 같은 사용자 계정에서 등록 앱의 메모리 전달을 대기합니다.

## 실패 시

- Python 경로 오류: 가상환경의 python.exe 파일을 찾기로 선택합니다.
- AI 폴더 오류: 이번 ZIP의 FaceAI 폴더에 wpf_bridge.py가 있는지 확인합니다.
- 모델 폴더 오류: 예전 model_cache 폴더 위치를 확인합니다.
- AI가 종료되면 비교 결과를 지우고 상태를 표시합니다. 진단 보기에서 마지막 메시지를 확인합니다.
- 전달 실패: 최신 인증 앱이 실행되어 있는지 확인합니다. 6.5 이후 카메라 미연결 상태에서도 임시 기준을 수신합니다. 초기화를 했다면 다시 전달합니다.
- 촬영 버튼 비활성: 정면 보정 후 등록을 시작했는지, 안내된 방향과 현재 방향이 일치하는지, 얼굴 상태·안정된 분석 횟수를 확인합니다.
- 상하·좌우가 반대이면 연결 종료 후 실행 환경 설정의 방향 보정 체크를 바꾸고 재연결합니다.

## 기존 서버 / PostgreSQL 기능

AccessControlServer의 직원 관리 기능은 기존과 같습니다.
기본 접속: `127.0.0.1:5432 / access_control_system / postgres`.
DB 비밀번호는 화면에서 직접 입력합니다. 코드·설정 파일에 저장하지 않습니다.
직원 등록·조회·수정은 실제 DB를 사용하고, 서버의 일부 이벤트 화면은 여전히 샘플 표시입니다.
이번 단계에 필요한 새 SQL은 없습니다. DB나 테이블을 다시 만들지 않습니다.

## 내부 연결과 다음 단계

WPF는 Python의 표준 입력/출력으로 JSON 명령·JPEG·상태를 주고받습니다.
Python은 카메라/UI 전송과 AI를 서로 다른 스레드에서 처리합니다.
두 WPF 앱의 임시 기준 전달은 현재 사용자 전용 Named Pipe입니다. 이 로컬 경로는 다음 단계의 TCP 서버 통신과 별개입니다.
서버 통신 단계에서는 등록·조회 요청을 서버로 전달하고 DB 저장·직원 매칭·권한 판정으로 확장합니다.
현재 얼굴 특징은 파일에 저장하지 않으며, 사람별 등록 관리 기능을 완료했다고 볼 수 없습니다.

`../validation/VALIDATION_STAGE6.md`에 빌드·검증 결과와 실제 Windows에서 확인할 항목을 정리했습니다.
