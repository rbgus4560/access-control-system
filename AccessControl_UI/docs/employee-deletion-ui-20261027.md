# 직원 삭제 대기 및 복원 화면

직원 목록의 사원번호·부서·직급·출입 허용 열 폭을 조정하고 가로 스크롤을 허용해 마지막 열 제목이 잘리지 않게 했다. 편집 영역의 등록 얼굴 설명과 마지막 수정 텍스트를 제거했다. 창 높이와 입력 여백을 조정했다.

직원 삭제 시 확인 안내를 표시하고 복원 가능한 삭제 대기로 전환한다. UI의 기본 유예기간은 7일이며 이 기간은 프로젝트 UX 기본값이다. 삭제 시 직원 활성/출입 권한을 해제하고 기존 얼굴 등록을 비활성화하지만 원본 정보와 특징은 보존한다. 삭제 대기 포함 체크로 대상을 다시 볼 수 있다. 대기 직원을 선택하면 남은 유예기간·예정일, 정보 복원 버튼과 비활성 빠른 삭제 버튼을 표시한다. 정보 복원은 직원 행을 복원하고 출입 권한을 자동 부여하지 않는다. 얼굴 등록은 재등록이 필요하다.

DB에는 Database/17_employee_delete_lifecycle.sql로 deleted_at과 delete_after를 추가해야 한다. 이 SQL은 실제 개인정보를 삭제하지 않는다. 기존 삭제 상태 행의 delete_after가 없으면 UI는 deleted_at + 7일을 안내하고 복원할 수 있다.

## 영구 삭제 제한

자동 승인 검토가 얼굴 특징 영구 삭제와 직원 정보 익명화를 포함한 7일 자동 삭제 구현을 거부했다. 사용자가 이 정확한 범위까지 명시적으로 승인하지 않았다는 사유다. 그 작업은 수행하지 않았으며 우회하지 않았다. 현재 코드는 삭제 대기와 정보 복원만 구현한다. 7일이 지나도 자동 영구 삭제하지 않는다. 빠른 삭제는 비활성 상태다. 영구 삭제 범위는 사용자 확인 후 별도 구현해야 한다.

## 검증

서버 빌드 경고·오류 0. 실제 DB 접근 없는 합성 직원 7명으로 전체 열과 일반/삭제 대기 편집 화면을 렌더링했다. 대기 상태에서 설명과 복원 버튼의 잘림을 확인하고 창 크기·여백을 보완했다. DB 마이그레이션, 실제 삭제 대기 전환과 복원 트랜잭션은 실행하지 않았다.


## 후속 명시 승인과 수동 영구 삭제 구현

사용자가 선택 직원의 정보·얼굴 데이터 영구 삭제를 명시적으로 선택했다. 이에 따라 삭제 대기 직원의 빠른 삭제를 활성화하고 대상 사원번호/이름, 삭제 범위, 복원 불가와 출입 기록 보존을 안내하는 확인 창을 추가했다. 트랜잭션 안에서 버전을 확인하고 사원번호를 임의 식별자 기반 삭제 표식으로 교체, 이름을 삭제된 직원으로 변경, 부서/직급 제거, 모든 등록의 face_templates 삭제, 등록 비활성화를 수행한다. 출입 기록의 FK를 보존하기 위해 persons/enrollment 식별 행 자체는 유지한다. purged_at 직원은 목록에서 제외하고 복원도 차단한다. 자동 영구 삭제는 추가하지 않았다.

Database/17_employee_delete_lifecycle.sql과 Database/18_employee_purge.sql이 필요하다. 18번은 purged_at 필드만 추가하며 데이터를 삭제하지 않는다. 이 작업에서는 실제 DB 연결·마이그레이션·삭제를 실행하지 않았다. 세 프로젝트 빌드 경고/오류 0. 직원 선택 콤보 높이가 줄어드는 문제는 공통/해당 컨트롤에 높이 34를 명시해 화면 미리보기로 확인했다. 실제 DB 트랜잭션 검증은 남아 있다. 위 영구 삭제 제한 문단은 당시의 이력이며 현재는 명시 승인한 수동 삭제 기능이 구현됐다.


삭제 대기 포함 체크박스를 사용자 요청으로 제거하고 목록 조회에서 대기 직원을 항상 포함하도록 변경했다. 영구 삭제된 직원은 기존과 같이 제외한다. 서버 빌드 경고/오류 0. 18번 SQL 적용을 시도했으나 저장된 server-startup.bin 연결 설정이 없어 DB 연결 이전에 중단됐다. 사용자 후속 지시로 실제 삭제는 사용자가 직접 진행하기로 했으며 이 작업에서는 DB 데이터나 스키마를 변경하지 않았다. 빠른 삭제는 얼굴만이 아니라 직원 기본 정보도 제거하는 기능이다.


삭제 무반응 피드백: 삭제 예외가 숨긴 StatusLabel에만 기록돼 사용자가 실패 이유를 알 수 없었다. 삭제/DB 세션 오류를 메시지 창으로 표시하고 필드 누락 메시지를 구체화했다. 18번 SQL은 17번의 deleted_at/delete_after도 IF NOT EXISTS로 추가해 18번만 적용해도 필요한 세 필드를 준비하게 변경했다. 사용자 DB의 실제 오류는 확인하지 못했으며 누락 여부는 미확인이다. 서버 빌드 경고/오류 0, 합성 삭제 대기 직원 미리보기에서 빠른 삭제 버튼과 복원 상태를 확인했다. 실제 삭제는 실행하지 않았다.
