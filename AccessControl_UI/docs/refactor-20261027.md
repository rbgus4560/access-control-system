# 2026-10-27 파일 구조 리팩토링

동작과 데이터 형식은 유지하고 큰 파일의 역할을 나눴다. 이번 작업 이전의 UI·DB 삭제 관련 수정은 보존했다. 인증 판정, 얼굴 특징, 운영 DB 스키마와 실제 데이터는 변경하지 않았다.

WPF 이벤트 이름과 기존 클래스 계약을 보존하기 위해 partial 파일로 분리했다. 세 앱에서 별도로 복사하던 동일한 테마를 Ui/StudioTheme.xaml 하나로 합쳤고 각 csproj에서 Theme/StudioTheme.xaml 경로로 링크한다. App.xaml의 리소스 URI와 실행 CMD 사용법은 동일하다. 다른 PC로 소스를 옮길 때는 기존처럼 AccessControl_UI 전체를 전달해야 한다.

## 검증

- 서버·인증 클라이언트·얼굴 등록 빌드: 경고/오류 0.
- FaceChecks: 얼굴 기준 형식, 5/9방향, 요청 계약, 타임라인 경계/빈 구간, 클립 계획 등 8개 묶음 PASS.
- HandoffChecks: 오프라인 수신과 로컬 이름 있는 파이프 전달 PASS.
- StartupChecks: 임시 설정만 사용한 DPAPI 저장/복구/교체/손상 거부/삭제 6개 검사 PASS.
- 합성 화면: 서버 9분할 배치 및 중복 방지 검사, 사이드바, 검색의 적용/제외/날짜 검사, 인증 클라이언트와 얼굴 등록 화면 캡처 확인.
- 이동한 7개 코드 블록은 분리 시 원문 해시를 비교해 내용 보존을 확인했다. 이후 카메라·기록 파일은 책임에 맞게 추가 분리했다.
- 실제 카메라·운영 DB·LAN 인증·녹화 재생은 이번 리팩토링 후 다시 실행하지 않았다. 이전 사용자의 현장 확인과 구분한다.

## 검증 중 환경 문제

StartupChecks는 제한 환경에서 임시 파일 교체가 거부됐고 HandoffChecks는 로컬 파이프 연결이 거부됐다. 실제 사용자 설정/운영 데이터를 사용하지 않는 동일 검사를 제한 밖에서 재실행해 통과했다. FaceChecks/HandoffChecks의 assets 파일 누락은 로컬 SDK 복원으로 해결했다. 최초 StartupChecks 빌드의 NuGet 취약점 피드 접근 경고는 실행 코드 오류가 아니며 앱 3종의 빌드 경고는 0이었다.
