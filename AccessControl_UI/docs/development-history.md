# 얼굴 인식 출입 통제 개발 과정

작성 기준일: 2026-10-21. 대상은 AccessControl_UI와 AccessControl_FaceAI_Python 두 프로젝트다. 이 문서는 소스와 기존 개발 기록을 바탕으로 초기 AI 검증에서 현재 통합 시스템까지의 흐름을 정리한다. 정확한 착수일, 전체 개발 기간, 팀 구성과 개인 기여도는 자료에 없어 확정하지 않았다. 기존 검증 결과와 이번 리팩토링 검증은 구분한다.

## 두 프로젝트의 관계

AccessControl_FaceAI_Python/face_ai_python은 카메라·얼굴 검출·자세·5방향 등록·동일인 비교를 독립 실행하는 초기 검증 도구다. AccessControl_UI/FaceAI는 이를 WPF·직원 DB·서버 최종 권한 판정·녹화·클립·전체 직원 검색으로 확장한 통합본이다. 둘은 기능과 실행 진입점이 달라 통째로 중복 파일로 판단해 삭제하거나 서로 덮어쓰지 않았다.

모델을 새로 학습했다는 근거는 없다. 사전학습 dlib·MediaPipe·ArcFace와 C# UI, 네트워크, DB, 영상 파일의 생명주기를 연결하는 것이 현재 프로젝트의 핵심이다.

## 시스템 처리 흐름

서버 PC의 등록 앱이 안내에 따라 얼굴 특징을 수집한다. 서버는 직원에 연결된 특징을 보호해 PostgreSQL에 저장한다. 카메라 클라이언트는 서버에서 전체 직원 기준을 받아 검증된 목록을 한 번에 적용하고, 현재 얼굴을 비교해 식별 후보를 보낸다. 서버는 최신 직원·등록·장치·출입 권한과 분석 시점을 확인한 뒤 판정과 기록을 확정한다.

영상은 별도 흐름으로 처리한다. 클라이언트는 실시간 JPEG를 보내고 MP4 원본과 JSON을 로컬에 보관한다. 서버에는 녹화 메타데이터를 동기화하고 필요한 시각의 원본이나 클립만 요청한다. 전송 파일의 크기·해시를 검사하며, 원본 보관은 완료 후 72시간 정책을 사용한다.

## 초기 AI 검증

초기 독립 도구는 dlib HOG 얼굴 검출, 5점 눈 정렬, MediaPipe 얼굴 메시와 자세 추정, ArcFace 512차원 특징 추출을 연결했다. 정면·상하·좌우 등록 기준과 현재 특징의 코사인 거리를 비교하고, 빈 영상·여러 얼굴·품질 미달을 거부하는 구조를 만들었다.

동일 입력 거리와 다른 테스트 인물의 거리 관찰은 기능 검증용 자료다. 두 장의 사진을 사용한 결과를 전체 정확도나 오인식률로 해석할 수 없다. 근거는 독립 도구의 VALIDATION.md와 tests 폴더다.

## 영상 표시와 추론 분리

AI 처리 지연이 영상 표시와 결과의 시점을 혼동하게 만들 수 있어 최신 프레임만 유지하는 전달 방식, 분석 프레임 표시와 오래된 결과 숨김을 도입했다. 초기 독립 도구의 별도 AI 프로세스 구조와 이후 WPF 브리지의 Python 작업자 스레드 구조는 버전별로 구분한다.

v3는 축소·그레이 영상에서 HOG를 수행하고 원본 영상에서 정렬했다. 과거 Linux의 단일 사진 준비 실행 후 측정은 검출 경로 비교 자료일 뿐 Windows 카메라 성능 보장이 아니다. 통합본에는 검출이 비어 있을 때 확대 재시도하는 후속 보완이 있으나 독립 도구에 자동 이식하지 않았다.

## WPF 연결과 준비 지연 진단

2026-10-17~18의 6단계 기록은 등록·인증 UI와 Python 연동, 준비 로그, 호출 스택 진단, import 순서 보완을 담고 있다. Windows에서 SciPy 네이티브 모듈 로딩 대기가 관찰되어 단계별 진단을 추가했다. 아래 방향 얼굴 검출에는 비어 있는 HOG 결과만 한 번 확대 재시도하도록 보완했다.

AI가 아직 연결되지 않았을 때 임시 얼굴 기준 전달이 실패한 문제에는 메모리 수신함과 준비 후 적용을 도입했다. 이것은 과거 단일 PC 절차이며 현재 주 경로는 서버 DB와 전체 기준 동기화다. 당시 Linux 계약 검사와 실제 Windows 흐름의 검증 여부를 구분한다.

## 네트워크와 DB 연결

7단계는 TCP 관측 정보·ACK·자동 재접속, 8단계는 직원 조회와 얼굴 특징 저장·복원, 9단계는 서버 최종 허가·거부와 출입 이벤트 기록으로 확장했다. 서버가 클라이언트의 일치 후보를 그대로 허가로 처리하지 않고 현재 DB 상태를 다시 확인하도록 분리했다.

2026-10-18 기록에는 5방향 DB 저장과 인증 앱 재실행 후 복원, 권한에 따른 GRANTED·DENIED, 얼굴 이탈 시 대기, 같은 시도의 반복 기록 방지에 대한 사용자 확인이 있다. 화면 한 프레임의 처리 시간은 평균 성능으로 일반화하지 않는다. DB 장애와 모든 예외 조건이 같은 날 전부 검증된 것은 아니다.

## 실시간 영상과 녹화 및 재생

10단계는 서버 JPEG 영상 수신, MP4 구간 녹화와 메타데이터, 타임라인·시각 재생, 이벤트 시각 연결, 클립 추출 순으로 기능을 쌓았다. MP4는 파일에 두고 DB에는 상태·시간·위치·크기·해시를 기록했다.

2026-10-18 사용자 기록에는 실제 MP4 재생, 약 60초 구간 분할, 앱 내부 재생, 이벤트 영상 연결, 5초 클립 재생과 LIVE 복귀 확인이 있다. 일부 직접 시각 탐색과 SQL 해시 대조는 개별 완료 보고가 없어 미확인으로 유지한다. 서버 종료 중 로컬 녹화와 복구 후 메타데이터 반영은 별도 시점에 확인되었다.

## 닷넷 전환과 보관 정책

2026-10-19에 .NET 10 대상으로 전환하고 시작 스크립트와 등록 앱 경로를 맞췄다. 이후 원본 72시간 보관 정책과 사용 중 파일 보호를 추가했다. 임시 파일 보관 검사 통과는 실제 운영 DB에서 DELETED로 전이되는 모든 조건을 검증한 것과 다르다.

새 SDK·실행 경로 전환 시 기존 DB, AppData, 얼굴 기준과 모델 캐시를 유지하는 방향을 따랐다. 실제 PC의 Windows 사용자에 연결된 DPAPI 특성 때문에 파일 복사만으로 다른 계정에 동일하게 복구된다고 가정하지 않는다.

## 연속 등록과 역할별 UI

10.7의 자유 순서 9방향에서 10.8의 안내형 연속 수집과 대표 샘플 선택으로 확장했다. 현재 안내형 대표 특징 9개는 정면 1개와 좌·우·상·하 각 2개이며 과거 9방향과 다르다. 2026-10-19 사용자 기록에 DB 저장 9/9와 클라이언트 수신 9/9가 있다. 당시 모든 사람 비교와 재시작 복원이 완료되었다는 의미는 아니다.

11단계부터 메인 영상과 상태를 중심으로 UI를 정리하고 설정·목록·이벤트 영상을 별도 창으로 옮겼다. 12.1~12.2는 서버·등록·인증 역할을 구분하고 안내한 방향만 수집하며 정면 복귀 후 진행하도록 보강했다. UI 컨트롤의 기존 부모를 분리하지 않은 등록 창 초기화 오류도 별도로 수정했다.

## 두 PC 전환과 장애 복구

12.0 이후에는 서버 PC에 DB·직원 관리·최종 판정·관제를, 클라이언트 PC에 카메라·AI·녹화·클립 작업을 분리했다. TLS 인증서 지문과 공유 키, DPAPI 보호, 파일 크기·SHA-256 확인, 요청 작업 보존과 재시도를 연결했다.

2026-10-20에는 Windows Schannel 개인 키 로딩 문제에 UserKeySet을 적용했고, 녹화 동기화는 구간별 실패 격리와 시도 순환으로 보완했다. 12.2.3은 정규 로컬 경로에서 원격 키로의 제한된 전환, 완료 불가능한 클립의 FAILED 처리, 같은 PC의 임시 파일과 서버 사본 분리를 포함한다. 실제 두 PC LAN 시연과 Linux 루프백·테스트 대역 검사는 서로 다른 검증이다.

## 자동 시작과 전체 직원 식별

12.2.4는 카메라·AI 연결 뒤 유효한 정면 상태를 확인해 자동 보정·비교를 시작하도록 했다. 12.3은 한 명을 선택하는 방식에서 전체 등록 직원을 자동 식별하는 방식으로 확장했다. 특징을 프레임당 한 번 추출하고 직원별 최소 거리와 2위 점수 차이로 모호성을 보류한다.

직원 목록은 약 10초 대기 주기로 재확인하고 변경 없는 특징은 재사용한다. 전체 검증이 끝난 목록만 C#과 Python에 적용하며, 서버 세션과 식별 토큰이 바뀌면 다시 확인한다. 상한 1000명은 구현 제한이며 실측 처리 성능이 아니다.

12.3 코드 정리 문서에는 다른 직원 자동 식별과 권한 없는 직원·미등록자 거부, 과거 동기화 대기 0, 결과가 없는 클립 요청 3건의 FAILED 정리가 사용자 환경 확인으로 기록되어 있다. 최신 소스 정리본 전체를 다시 현장 검증했다는 뜻으로 확대하지 않는다.

## 이번 리팩토링과 파일 정리

2026-10-21에는 두 프로젝트의 face_logic.py에서 입력 특징을 각 샘플마다 반복 정규화하는 부분을 reference_distances 함수로 분리했다. 입력 정규화는 비교 호출당 한 번 수행하고, 샘플 검증·순서·거리 계산·동점 선택은 유지했다. 사용자 체감 속도 개선율은 측정하지 않았다.

C# GallerySynchronizer는 연결 세대 확인과 상태 표시를 함수로 분리하고 폴링 간격을 이름 있는 상수로 만들었다. 부분 기준 보류·캐시 재사용·서버 재시작 처리 순서는 유지했다. 두 폴더에 .gitignore를 추가했다.

확인된 생성 파일 134개, 11070282바이트를 8개 디렉터리에서 제거했다. 대상은 obj, Python __pycache__, 실행 중이 아닌 등록 앱 및 검사 앱의 bin이다. 실행 중인 서버·인증 앱의 bin은 유지했다. 모델·모델 캐시·카메라 데이터·DB·이력 문서·검사 소스와 과거 진입점은 역할이나 참조가 있어 보존했다. 삭제 내역은 바탕화면 AccessControl_Refactor_20261021/cleanup-manifest.json에 있다.

인증 앱의 기본 출력 빌드는 실행 중 EXE 잠금으로 실패했다. 앱을 강제 종료하지 않고 별도 출력 경로로 빌드해 통과했다. 현재 실행 중인 프로세스가 수정 소스를 새로 로드한 것은 아니므로 다음 정상 종료·시작 때 시작 스크립트로 다시 빌드한다. obj 삭제 후에는 --no-restore 대신 기본 시작 스크립트의 일반 dotnet build를 사용한다.

이번에는 실제 사람 얼굴 인식, USB 카메라, 실시간 DB 권한 변경, 학교 LAN, 최신 WPF 창의 화면 동작과 운영 파일의 만료 삭제를 새로 시험하지 않았다. 검사 중 표시된 Simulated model error 등은 오류 거부 경로를 확인하는 의도된 입력이다.

문서에서 확인되는 설계상의 교훈은 영상 표시와 분석 시점 분리, 후보와 최종 권한의 분리, 완성된 기준만 공개하는 상태 관리, 실패 구간 격리와 공정한 재시도, 영구 실패와 재시도 가능한 장애 구분, 파일 소유 주체별 정리 범위 분리다. 이것을 본인의 경험으로 발표하려면 실제 담당 범위와 시도 과정을 확인해야 한다.
