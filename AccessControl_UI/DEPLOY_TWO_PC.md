# 12.2 두 PC 배치·실행 안내

이 버전은 같은 교실 LAN의 서버 1대와 카메라 클라이언트 1대(CAM-01)를 대상으로 한다. 기존 DB가 있는 학교 PC가 서버다. 새 PC에는 PostgreSQL을 설치하지 않는다. 서버와 클라이언트 모두 이번 12.2 소스를 사용한다.

## 역할과 데이터 위치

| 구분 | 서버·관리 PC (기존 학교 PC) | 구역·카메라 클라이언트 PC |
|---|---|---|
| 실행 앱 | AccessControlServer.exe, 필요할 때 FaceEnrollment.exe | FaceRecognition.exe |
| DB | 기존 PostgreSQL, localhost:5432 | 직접 연결 없음, DB 비밀번호 불필요 |
| 얼굴 등록 | 직원·권한 관리, USB 카메라로 연속 등록, 기존 Windows 계정에서 특징 암호화 저장 | 읽기 전용 직원 목록에서 비교할 한 명의 기준 수신 |
| 인증 | 최신 등록·직원 활성·권한·분석 시각을 확인한 최종 허가/거부, DB 기록 | 카메라·Python AI·1:1 얼굴 비교, 결과 전송, 서버 판정 표시 |
| 실시간 영상 | 클라이언트 JPEG 수신·관제 | 자체 카메라 JPEG 전송 (최대 5fps), 원본 녹화 별도 |
| 녹화 원본 | 메타데이터만 DB 저장, 재생 요청 시 해당 원본 사본 수신 | 로컬 MP4·JSON 보관, 완료 후 72시간 자동 정리 |
| 타임라인 | DB 완료 구간 조회, 구간 ID로 원본 요청·크기/해시 검증 후 Windows 재생 | 요청된 완료 원본 전송 |
| 클립 | 시간 범위 요청, 서버 사본 수신·SHA-256 검증·DB 결과 저장 | 로컬 원본에서 MP4 추출, 서버 수신 확인 후 임시 클립 삭제 |

영상 파일 자체를 PostgreSQL BLOB에 넣지 않는다. DB에는 구간 ID·상태·시간·크기·파일 키/클립 경로·해시를 기록한다. 클라이언트 원본 키는 `client://CAM-01/<구간ID>`이며 서버 로컬 파일 경로가 아니다.

서버 등록용과 클라이언트 인증용 Python 기술은 동일하다. dlib·MediaPipe·DeepFace/ArcFace와 등록 샘플 선택 방식·비교 임계값은 이번 네트워크 전환에서 바꾸지 않았다. 현재는 선택한 직원 한 명과 비교하는 1:1 방식이다. 여러 등록자를 자동 식별하는 1:N 검색은 구현 범위가 아니다.

## 1. 정상 기준 버전과 데이터 보존

1. 기존 앱 세 개와 카메라를 종료한다. 정상 동작한 폴더를 별도 이름으로 복사해 둔다.
2. 이번 ZIP은 **새 폴더**에 푼다. 예: 바탕화면 `AccessControl_UI_12_2`. 11.1 소스 폴더에 덮어쓰면 이번에 제거한 옛 재생·클립 창 파일이 남을 수 있으므로 새 폴더를 권장한다.
3. 기존 서버의 Windows 사용자 계정을 그대로 사용한다. DB 암호화 특징은 Windows DPAPI CurrentUser에 연결되어 있다. DB를 다른 PC로 복사하는 작업은 이번 배치에 포함하지 않는다.
4. PostgreSQL DB와 `%LOCALAPPDATA%\AccessControlSystem` 폴더를 삭제하지 않는다. 기존 모델 캐시와 Conda 환경도 유지한다.

새 폴더에서 기존 AI 설정이 이전 UI 폴더의 FaceAI를 가리킬 수 있다. 서버 등록 설정과 클라이언트 카메라 설정에서 **이번 폴더 안 FaceAI**를 다시 선택한다. 모델 캐시는 기존 경로를 사용해도 된다.

## 2. 서버 DB에 추가 SQL 적용

기존 DBeaver의 `access_control_system` 연결에서 다음 파일 전체를 SQL 스크립트로 실행한다.

`Database/15_recording_client_metadata.sql`

완료 결과에 `client_metadata / jsonb`가 나오는지 확인한다. 기존 행과 얼굴 데이터는 유지한다. 초기 테이블 생성 SQL을 다시 실행하지 않는다. 13·14번은 앞에서 적용한 그대로 유지한다. 실행 후 DB 백업으로 복원하지 않는 한 추가 열은 남겨도 기존 11.1 코드와 호환된다.

## 3. 서버 PC 실행

1. .NET 10 SDK가 설치된 기존 학교 PC에서 `Start_Server.cmd` 실행. 서버와 등록 앱을 빌드하고 **서버 창만** 연다.
2. 서버 창 제목 `12.2 · 서버 관제` 확인.
3. 왼쪽 `서버 설정`의 `DB·관리자` 탭에서 기존 DB 정보 `127.0.0.1 / 5432 / access_control_system / postgres`와 비밀번호로 DB 연결. 기존 관리자를 선택한다.
4. `서버 설정`의 `클라이언트 연결` 탭에 있는 `서버 IPv4`에서 **다른 PC가 접속할 수 있는 학교 LAN 주소**를 고른다. 가상 어댑터·VPN 주소나 127.0.0.1을 사용하지 않는다. 여러 주소가 있으면 Windows `ipconfig`의 실제 연결 어댑터 IPv4와 대조한다.
5. 기본 포트 5050으로 `TCP 서버 시작`을 누른다. 5050(판정)·5051(JPEG)·5052(얼굴/녹화 API·원본/클립 요청)을 함께 연다.
6. `클라이언트 연결 코드 복사`를 누른다. 코드에는 서버 IP·포트·장치 공유 키·인증서 지문이 들어 있다. 비밀번호처럼 취급하고 소스 저장소·공개 캡처에 넣지 않는다. 서버 인증서 개인 키와 DB 비밀번호는 코드에 포함되지 않는다.

연결 키/인증서는 `%LOCALAPPDATA%\AccessControlSystem\network\server.bin`에 DPAPI 보호 저장한다. 서버를 다시 실행해도 같은 계정에서는 유지한다. 파일을 임의로 지우면 새 코드로 다시 연결해야 한다. 인증서 유효기간은 생성 후 2년이다.

## 4. 클라이언트 PC 준비와 연결

1. 같은 ZIP을 다른 PC의 새 폴더에 푼다. .NET 10 SDK가 필요하다. PostgreSQL·DBeaver 설치는 필요 없다.
2. 이 PC에 Python 환경이 없다면 Anaconda Prompt에서 `FaceAI\setup_environment.bat`을 실행한다. 기존 `access_face_ai` 환경이 있으면 새로 만들지 말고 우선 준비 검사를 한다. 모델은 다운로드하거나 기존 정상 모델 캐시를 복사해 사용할 수 있다.
3. `conda activate access_face_ai` 후 이번 `FaceAI` 폴더에서 `python check_setup.py --prepare`. 모델 로딩과 blank-frame PASS 확인. 환경 폴더 전체를 다른 Windows 계정 경로로 단순 복사하지 않는다.
4. `Start_Client.cmd` 실행. **인증 앱만** 열린다. 제목의 `12.2 · 구역 인증 클라이언트` 확인.
5. 설정의 서버 연결 탭에서 복사한 전체 코드를 붙여넣고 `연결 코드 적용`. 주소·포트는 코드에 따라 표시된다. 클라이언트 PC 자신의 주소를 넣지 않는다.
6. `서버 연결`을 누른다. 왼쪽 `인증 기준 선택` 목록에서 기존 얼굴 등록 직원을 고르고 `선택 직원 얼굴 불러오기`를 누른다.
7. 카메라/AI 설정에서 이 PC의 `access_face_ai\python.exe`, 이번 FaceAI 폴더, 모델 캐시, USB 카메라 번호(보통 0)를 지정하고 연결한다. 본인 비교와 서버 최종 판정·서버 영상 수신을 확인한다.

클라이언트 연결 코드는 해당 PC의 `%LOCALAPPDATA%\AccessControlSystem\network\client.bin`에 DPAPI 보호 저장한다. 다음 실행 때 다시 붙여넣을 필요는 없지만 인증·영상 연결 버튼은 눌러야 한다. 얼굴 기준도 다시 조회·불러온다.

`인증·영상 연결 종료`는 판정/실시간 JPEG 통신을 중지한다. 카메라·로컬 녹화·녹화 정보 동기화·영상/클립 요청 연결은 계속 동작한다. 모든 클라이언트 통신과 녹화를 종료하려면 클라이언트 앱을 닫는다.

## 5. LAN·방화벽 확인

서버 앱을 시작한 상태에서 클라이언트 PowerShell에서 실제 서버 IP로 확인한다.

```powershell
Test-NetConnection 192.168.0.10 -Port 5050
Test-NetConnection 192.168.0.10 -Port 5051
Test-NetConnection 192.168.0.10 -Port 5052
```

위 주소는 **예시**다. 실제 서버 주소로 바꾼다. 같은 교실이어도 학교의 단말 격리/VLAN 정책에 따라 연결되지 않을 수 있다. 세 포트 모두 `TcpTestSucceeded : True`가 필요하다. 이 검사는 포트 도달 여부이며 연결 코드 인증 성공을 뜻하지는 않는다.

Windows 방화벽 허용이 필요한 경우 서버의 관리자 PowerShell에서 이번 폴더로 이동한 뒤 **실제 클라이언트 IP**를 넣어 제공 스크립트를 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Allow_Server_LAN.ps1 -ClientIP 192.168.0.20
```

이 스크립트는 지정한 한 클라이언트 주소에서 현재 Debug 서버 실행 파일의 세 앱 포트로 들어오는 통신만 허용한다. 실행 폴더·기본 포트·클라이언트 IP가 달라지면 그에 맞춰 다시 설정한다. PostgreSQL 5432는 열지 않는다. 학교 정책에 막히면 담당자 확인이 필요하며 방화벽 전체 해제로 해결하지 않는다.

양쪽 PC의 Windows 날짜·시간도 자동 동기화한다. 기존 freshness 판정은 두 PC 시각을 사용하므로 시계가 어긋나면 영상이 숨겨지거나 출입 판정이 대기할 수 있다.

## 6. 얼굴 등록·수정

서버에서 `직원 관리`로 직원·활성·권한을 관리하고 `얼굴 등록`을 연다. 서버 PC에 등록용 카메라가 필요하다. 카메라가 한 개뿐이면 등록 때만 서버로 옮기고 이후 클라이언트에 다시 연결해도 된다.

등록 앱에서 직원 조회·선택 후 연속 등록·DB 저장. 기존 방식대로 정면 1개와 좌우·상하 각 2개 대표 특징을 저장한다. 이번 12.2는 안내된 방향만 수집하며 왼쪽·오른쪽·위 수집 후 정면 복귀를 확인하고 다음 방향으로 진행한다. 저장 후 **클라이언트에서 목록 새로고침·새 얼굴 불러오기**를 한다. 등록 직후 기준을 실행 중 클라이언트에 자동 밀어넣는 기능은 없다. 기존 임시 기준 전달 버튼은 제거했다.

## 7. 녹화·재생·클립

- 원본: 클라이언트 `%LOCALAPPDATA%\AccessControlSystem\recordings\CAM-01\UTC날짜\구간ID.mp4`, 옆 JSON이 재동기화용 메타데이터다. 현재 약 60초 단위, 10fps 녹화.
- DB에는 클라이언트가 보고한 녹화 상태를 저장한다. READY 메타데이터를 받았다는 사실과 서버가 실제 파일을 받아 해시를 검증했다는 사실은 구분한다.
- 서버가 꺼져 있어도 클라이언트 앱·카메라가 실행 중이면 로컬 녹화·보관 정리는 계속된다. 서버 재실행 후 DB 연결·TCP 시작 시 클라이언트가 자동 재접속하고 미전송 녹화 정보를 재시도한다. 앱과 PC가 모두 꺼진 동안의 촬영은 하지 않는다.
- 서버 `타임라인·클립`: 날짜 조회 후 파란 완료 구간/시각 선택. DB 목록을 읽고 해당 구간의 원본 사본을 클라이언트에 요청한다. 파일이 크면 수신 후 재생까지 시간이 필요하다. 아직 RECORDING인 현재 구간은 완료 후 조회한다.
- 서버 `출입 기록` 창의 `선택 기록 영상`도 같은 서버 재생 창을 연다. 클라이언트 화면을 원격으로 여는 named pipe는 더 이상 사용하지 않는다.
- 기존 서버 PC에 남아 있는 단일 PC 버전 원본은 DB 목록·로컬 파일이 일치하면 재생할 수 있다. 이 옛 원본을 새 클라이언트로 옮기거나 자동 정리 작업까지 이전하지는 않는다. 보존 중인 자료를 확인한 뒤 별도로 정리한다.
- 재생 캐시: 서버 `%LOCALAPPDATA%\AccessControlSystem\remote_cache\CAM-01`. 해당 원본의 종료 후 72시간을 기준으로 캐시도 정리하며 사용 중 파일은 보류한다.
- 클립: 서버 재생 창에서 시작·종료 시각을 지정해 요청. 최대 5분, 같은 날짜 범위. 클라이언트가 원본을 찾아 Python으로 MP4를 추출하고 서버에 보낸다. 서버의 크기·SHA-256 검증과 결과 정보 저장 후 수신 확인을 보내면 **클라이언트의 그 임시 클립만** 삭제한다.
- 서버 클립: `%LOCALAPPDATA%\AccessControlSystem\clips`. 원본 72시간 정리 대상에서 제외한다. 클립은 관리자가 별도로 보관/정리한다.
- 서버에 접수된 클립 요청은 `*.remotejob.json`으로 남는다. 전송 중 끊기거나 DB 완료 반영이 실패하면 서버 실행·DB/클라이언트 재연결 후 자동 재시도한다. 사용자가 창을 닫아도 접수된 요청은 남는다. 원본이 이미 삭제됐거나 설정이 잘못되면 실패/대기가 계속될 수 있으므로 원본 보관 상태와 Python 설정을 확인한다. 실패 요청 취소 전용 UI는 이번 범위에 없다.
- 추출·전송 파일 최대 500MB, 양쪽 여유 공간 기준 20GiB. 손상/중단 파일은 `.part` 상태로 정리하고 완료 파일로 사용하지 않는다.

## 범위와 적용 상태

이번 구현은 2PC용 소스·TLS 연결·파일 전송·역할 분리다. 여러 카메라의 동시 연결·1:N 얼굴 검색·인터넷 배포·위변조 방지용 라이브니스는 포함하지 않는다. 실제 Windows 두 PC·USB 카메라·방화벽·DPAPI·MediaElement MP4 재생은 아래 체크리스트로 확인해야 한다. 서버용/클라이언트용 코드를 수정했다고 실제 현장 시연까지 검증된 것은 아니다.

기존 아래 숙이기 검출 문제와 등록 샘플의 실제 본인/타인 정확도 평가는 별도 개선 항목으로 유지한다.

## Windows 두 PC 확인 순서

1. 서버 DB 연결·기존 관리자·TLS 서버 시작, 클라이언트 세 포트 도달 확인.
2. 연결 코드 적용·직원 조회·기존 5/9개 얼굴 불러오기. 틀린 코드에서는 연결되지 않는지 확인.
3. 클라이언트 카메라·AI·본인/타인·얼굴 이탈·다중 얼굴, 서버 최종 허가/거부·DB 기록·JPEG 수신.
4. 완료 원본이 생길 때까지 약 1분 촬영. 클라이언트 동기화 대기 0, 서버 녹화 DB READY 확인.
5. 서버 타임라인 재생·출입 이벤트 시각 재생. 서버에 요청한 구간 사본이 생기며 클라이언트 원본도 남는지 확인.
6. 5초 클립 요청. 서버 MP4 기본 플레이어 재생·DB exported_clips READY·파일 해시·클라이언트 원본 유지 확인.
7. 서버 앱 전체 종료 후 클라이언트 촬영. 서버 재실행·DB 연결·TCP 시작 후 자동 재접속·녹화 동기화·그 구간 서버 재생 확인.
8. 클립 전송 중 네트워크 중단 후 복구. 잘못된 완료본 없이 재시도되는지 확인. 정상 버전 백업은 이 확인이 끝날 때까지 유지.
